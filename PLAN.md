# OpenSCAD Visual CAD App — Implementation Plan

## Context

Jordan wants to build a desktop CAD application, styled after Onshape, where users visually select/drag/manipulate parts in a 3D viewport, but the persisted artifact is always real, valid OpenSCAD (`.scad`) source code — not a proprietary format. Because OpenSCAD supports user-defined `module` blocks, custom toolbar tools fall out naturally: any module the user (or an imported library) defines should automatically become a draggable/clickable tool.

Before any design work, terminology was verified against the official OpenSCAD User Manual to make sure the mental model driving the app is correct:

- **`module`** — a named, reusable block that performs actions (generates geometry) and returns **no value**: `module name(params) { ... }`, instantiated as `name(args);`, can wrap children via `children()`. This is the correct term for "a reusable part/section" and for "custom toolbar tools."
- **`function`** — returns a single computed value, no geometry: `function name(params) = expr;`. Distinct from a module; custom toolbar tools should be built from modules, not functions.
- **Modifiers** `# % ! *` — highlight / transparent-ghost / show-only-this / disable, prefixed onto any statement.
- **`use <file>` vs `include <file>`** — `use` imports only modules/functions (no variables, no executed geometry) and is the right directive for "a library of custom tools"; `include` executes everything.
- Primitives (`cube`, `sphere`, `cylinder`, `polyhedron`, `square`, `circle`, `polygon`, `text`), transforms (`translate`, `rotate`, `scale`, `mirror`, `color`), booleans (`union`, `difference`, `intersection`), extrusions (`linear_extrude`, `rotate_extrude`).

This is a **greenfield project**. The following architecture decisions were made explicitly by Jordan and are treated as fixed constraints, not open questions:

1. **Electron** for the desktop shell (chosen over Tauri specifically so the bundled Chromium gives consistent WASM/SIMD behavior across OSes, since the render engine depends on it).
2. **Real OpenSCAD compiled to WebAssembly** (`openscad-wasm`) as the geometry/render engine — not a reimplemented JS/WebGL CSG library — so the preview is always byte-for-byte what real OpenSCAD would produce.
3. **MVP scope = "broad" tier**: primitives + transforms + booleans + extrusions + user-defined custom modules surfaced as toolbar tools, with full bidirectional text↔visual sync — this is the actual v1 target.

Two hard technical risks were identified and verified before committing to this plan:
- Does a usable OpenSCAD parser exist for JS/TS? **Yes** — [`openscad/tree-sitter-openscad`](https://github.com/openscad/tree-sitter-openscad) is an actively maintained, org-owned incremental tree-sitter grammar (MIT, JS/Rust/Python/Go bindings) — confirmed live via GitHub.
- Is there a usable WASM build of OpenSCAD with a documented invocation contract? **Yes** — [`openscad/openscad-wasm`](https://github.com/openscad/openscad-wasm), an Emscripten ES6 module: write source to a virtual FS, `callMain(["/input.scad", "--enable=manifold", "-o", "out.stl"])`, read the output back — confirmed live via GitHub, including Manifold-backend support for fast CSG.

## Recommended tech stack

| Layer | Choice | Why |
|---|---|---|
| Shell | Electron (contextIsolation on, no nodeIntegration in renderer) | Fixed constraint; main process only handles fs/menus/window chrome |
| UI | React + TypeScript | Matches the proven `openscad-playground` (OpenSCAD org's own reference UI) pattern of React+Monaco+WASM |
| 3D viewport | `@react-three/fiber` + `@react-three/drei` (TransformControls, OrbitControls) | Declarative scene graph maps directly onto the AST-derived model; gizmos ship out of the box |
| Geometry engine | `openscad-wasm` (Manifold backend, `--enable=manifold`) in a dedicated Web Worker | Fixed constraint; Manifold backend gives the CSG speed needed for iterative editing |
| Mesh transport | Binary STL from WASM → hand-rolled/`STLLoader` → `BufferGeometry` | Simplest format the WASM CLI already emits natively |
| Code editor | Monaco (`@monaco-editor/react`) with a custom OpenSCAD Monarch tokenizer | Same choice as `openscad-playground`; supports decorations for selection sync and inline parse-error diagnostics |
| Parser | `web-tree-sitter` + compiled `tree-sitter-openscad.wasm` | CST with incremental re-parse and full trivia (whitespace/comment) preservation — the property bidirectional sync depends on |
| Semantic layer | Hand-written `scad-ast` walking the CST into typed nodes (ModuleCall, Transform, BooleanOp, ModuleDef, Modifier, etc.) | Tree-sitter gives a generic CST; a thin typed layer on top is needed to reason about "this is a `translate` with 3 args and one child" |
| State | Zustand for UI/selection/camera state; CST/AST/scene-graph held in a dedicated store outside React, subscribed via selectors | The CST is large and patched incrementally — shouldn't live directly in React state or be duplicated across Monaco/scene-graph |
| Packaging | electron-builder; WASM/font/MCAD assets shipped as loose `extraResources`, not bundler-inlined | Multi-MB WASM assets; loose files make future OpenSCAD-WASM version bumps a drop-in replacement |

## Package boundaries (monorepo, pnpm/npm workspaces)

```
packages/
  scad-cst/              parse(text) -> Tree; incremental edit(tree, edits) -> Tree (wraps web-tree-sitter)
  scad-ast/               CST -> typed semantic AST (ModuleCall, ModuleDef, Transform, BooleanOp, Modifier, ...)
  scad-codegen/           typed node -> source fragment; targeted minimal-diff patch engine (nodeId, newParams) -> byte-range edit
  scene-graph/            AST -> UI scene tree: stable node IDs, resolved transform matrices, modifier flags, dirty-tracking
  module-introspection/   scans local file + everything reachable via `use <path>`; infers param widgets; emits ToolDefinition[]
  render-worker/          Web Worker wrapping openscad-wasm; per-node isolated render + full-document render, job queue w/ cancellation
  viewport/               r3f scene; per-node mesh cache; raycast selection; TransformControls binding; modifier material overrides
  toolbar/                built-in ToolDefinition table (cube, sphere, ... union, ... extrude) + dynamic custom-module tools
  editor-pane/            Monaco wrapper; syntax highlighting; diagnostics; decoration sync; cursor<->node mapping
  app-shell/              Electron main + preload: file open/save, `use`d-file watching (chokidar), IPC surface
  desktop-ui/             Electron renderer root; composes viewport+editor-pane+toolbar; owns the central document store
```

Dependency direction: `scad-cst` → `scad-ast` → {`scene-graph`, `scad-codegen`, `module-introspection`} → {`viewport`, `toolbar`, `editor-pane`} → `desktop-ui`. `render-worker` depends only on `scene-graph`, keeping parsing/codegen unit-testable with plain `.scad` fixtures, no Electron/DOM needed.

## Bidirectional sync architecture

**Single source of truth**: the CST (tree-sitter tree) over the raw text buffer, held once in `desktop-ui`'s document store. The semantic AST, scene-graph, Monaco's displayed text, and viewport meshes are all derived/cached projections — never independently-owned copies.

**Text edit path** (Monaco → world): content-change delta → `tree.edit()` incremental re-parse (touches only the changed subtree, tolerates transient invalid syntax via tree-sitter's ERROR nodes) → `scad-ast` re-derives only affected subtrees → `scene-graph` emits a minimal changeset → `viewport`/`toolbar` update only the invalidated nodes. Mid-typing invalid syntax keeps showing the last-known-good mesh for affected nodes rather than erroring; full re-render is debounced (~300-500ms idle).

**Visual edit path** (gizmo/toolbar → world): a UI action targets a scene-graph node id; `scad-codegen`'s targeted patch engine computes the *minimal* text replacement (e.g. `translate([1,2,3])` → replace only the `3` byte range with `3.5`, leaving all other formatting untouched); that edit is applied to the CST via the **same** `tree.edit()` path as the text-edit case, so there is exactly one re-derivation pipeline, not two divergent ones. Monaco's model is updated via `executeEdits(...)` (preserves undo-stack + cursor position) with the identical range/text.

**Comment/whitespace preservation**: achieved by construction — edits are always expressed as `(startByte, endByte, newText)` replacements against specific CST node ranges, so anything not touched (including comments inside untouched argument lists) is never rewritten. This is chosen over a "regenerate whole file from AST + pretty-print" approach, which would require a much harder 100%-round-trip-safe pretty-printer.

**Node identity across edits**: each scene-graph node gets a stable UUID assigned via a structural fingerprint (path-from-root by child-index + call-name, falling back to argument-similarity fuzzy matching), diffed old-vs-new on every re-derive so selection/gizmo state survives edits elsewhere in the file. This side-map is ephemeral/session-only — never written into the `.scad` file.

## Per-node selection & manipulation strategy

The hard problem: `openscad-wasm` only ever emits one flattened mesh, with no per-source-node correlation. Solution — **isolated per-node render passes + a two-layer viewport**:

1. Every top-level statement (and, lazily on selection-expand, its direct geometry children) gets its own **isolated render**: `render-worker` slices that node's exact source byte range, prepends any needed context (variable assignments, `use`/`include` directives — cheap, no geometry side effects), and runs `openscad-wasm` on that synthetic single-node program alone. Result: a mesh containing exactly that node's geometry, with known provenance by construction.
2. Results are cached in `Map<nodeId, {geometry, boundingBox, sourceHash}>`; re-render is skipped whenever the node's own source+context hash is unchanged, so editing one node doesn't invalidate its siblings.
3. **Selection/gizmo layer**: the isolated meshes, invisible or shown as thin outlines, used purely for raycast hit-testing (click → nodeId) and gizmo placement. **Display layer**: the single full-document composite render (real `union`/`difference` fidelity), the one actually shown as the visible surface. Clicking always raycasts against the selection layer — this sidesteps ever needing to attribute triangles of a fused/composite mesh back to a source node.
4. **Gizmos edit AST parameters directly, never mesh vertices.** Dragging a translate gizmo on node N updates node N's `translate([x,y,z])` arguments directly (converting the world-space drag delta into N's local frame via the already-known ancestor transform chain) — the mesh is only ever used for "where to draw the gizmo," never as the edited object. This is the key move that avoids reverse-engineering transforms from geometry.
5. Modifiers map to render/material treatment: `%` → transparent ghost material, excluded from the "real" computed output; `#` → highlight overlay; `!` → short-circuit the full-document render to just that subtree (mirrors OpenSCAD's own semantics); `*` → excluded entirely, shown as a translucent dashed ghost for discoverability.
6. Performance: special-case pure rigid-transform drags (translate/rotate/scale/mirror) to skip WASM entirely during the drag (just move the cached mesh's `Object3D` transform) and only trigger a real re-render on drag-end, since a pure transform of already-known geometry is analytically knowable without re-running CSG.

## Custom module auto-toolbar

1. `module-introspection` scans the open file plus everything transitively reachable via `use <path>` (resolved relative to the document, matching OpenSCAD's own resolution rules; watched live via `chokidar` through the Electron main process's fs IPC).
2. For each `ModuleDef`, extract name/params/defaults/source location.
3. Infer a UI widget per parameter from its default value: boolean literal → checkbox; numeric → number field (degree-slider if name/usage suggests an angle); 3-vector → XYZ widget; string → text field; no default → required generic field, cross-checked against existing call-site argument shapes elsewhere in the project as corroborating evidence.
4. Emit a `ToolDefinition` (same shape used for built-ins) into a distinct "Custom" toolbar section.
5. Instantiation reuses the exact same insertion code path as built-in primitives in `scad-codegen` (inserts `name(param: value, ...)` using named arguments for readability) — custom and built-in tools differ only in where their `ToolDefinition` came from, not in how they're inserted or rendered (the isolated-render step just also prepends the relevant `use` directive so the module is in scope).

## Toolbar

Fixed Onshape-style sections mapping 1:1 to real OpenSCAD operations — no invented abstractions:
- **2D primitives**: square, circle, polygon, text
- **3D primitives**: cube, sphere, cylinder, polyhedron
- **Transform**: translate, rotate, scale, mirror, color
- **Boolean**: union, difference, intersection
- **Extrude**: linear_extrude, rotate_extrude
- **Custom** (dynamic, from module-introspection)

Boolean-op tools operate on multi-selected existing nodes via a "wrap selected source ranges in a new block" structural edit (`difference() { <verbatim selected text> }`) — still a targeted/minimal patch, not a full-file regen.

## Constraints layer ("SCAD+": valid SCAD + app-owned annotations)

Two distinct kinds of constraint, handled very differently, both persisting into the same single `.scad` file with no separate save format:

1. **Directional/DAG constraints** (distance, offset, alignment, "N copies with gap X") — these require no solver at all. They're just SCAD variables and expressions the app generates via `scad-codegen`, e.g. `gap = 10; translate([partA_w + gap, 0, 0]) cube(10);`. The constraint *is* the code the moment it's written — nothing extra to persist, nothing to rehydrate. This is in scope for v1 and needs no new package beyond what's already planned (`scad-codegen`, `scene-graph`).
2. **Solver-based constraints** (tangency, mutual/cyclic relationships — the kind a real 2D sketch constraint solver handles) — OpenSCAD has no language concept of "solve this system," so the app must run its own constraint solver at edit time and write the **solved numeric result** into the file as plain values/expressions. To preserve the *intent* ("these two must stay tangent") for future re-editing, the app also emits a structured comment adjacent to the affected code, e.g.:
   ```
   // @constraint: tangent(circleA, circleB)
   ```
   This is inert to real OpenSCAD (just a comment) but is parsed back out by the app (via `scad-ast`'s comment-node handling) to rehydrate the constraint graph on reopen. This makes the `.scad` file itself the constraint database — no sidecar file — at the cost of the annotation being an app-owned convention that only this app understands or enforces.
   - **Staleness handling**: if the file is hand-edited outside the app (or in vanilla OpenSCAD) such that the annotated values no longer satisfy the constraint, the app must detect the mismatch on reopen/rescan and prompt to re-solve rather than silently trusting stale annotations.
   - **New package**: `constraints/` — constraint type definitions (distance, parallel, perpendicular, tangent, coincident, symmetric), a solver (start minimal: Newton-Raphson over the small DOF sets these operations actually need, not a general-purpose sketch solver), DOF bookkeeping, and over/under-constrained detection surfaced in the UI.
   - **Scope decision**: solver-based constraints are explicitly **out of v1** — v1 ships directional/DAG constraints only, which cover distance/alignment/array use cases with zero solver risk. Full solver-based constraints become their own later milestone (see M12) once the core editor is stable, since a geometric constraint solver is a substantial subsystem in its own right.

## Fillets/chamfers (v1, M13): BOSL2 integration

OpenSCAD has no native "select an edge, round it" primitive the way a B-rep CAD kernel (Fusion, SolidWorks, Onshape) does — CSG/mesh boolean engines like Manifold don't carry edge identity to blend. Two real ways to get fillets in plain OpenSCAD, decided 2026-09-11 (with Jordan, weighing selectivity vs. dependency cost):

1. **`minkowski()` with a sphere** — rounds *every* convex edge of a shape uniformly; not selective, and expensive on the Manifold backend at anything beyond simple shapes. No new dependency, but doesn't match what users expect from "fillet this one edge."
2. **[BOSL2](https://github.com/BelfrySCAD/BOSL2)** — a widely-used third-party OpenSCAD library providing real `fillet()`/`chamfer()` modules with edge/face selection (positional keywords like `edges=TOP+FRONT`, not literal click-to-select, but far closer to real CAD fillet behavior than Minkowski). Chosen over option 1 as the target — it stays inside the "always valid, editable plain SCAD" constraint (BOSL2 is itself just `.scad` source, pulled in via `use`, consistent with the project's existing library-import model from "Custom module auto-toolbar" above), and its selectivity is what actually delivers a "full CAD workflow" feel.

**Why this is its own milestone, not folded into M6/M10**: BOSL2 support means (a) bundling/vendoring the library and resolving its `use` path reliably across both dev and the packaged Electron app (same asset-shipping question as the WASM/font/MCAD assets noted in the tech-stack table), (b) toolbar/gizmo UI for BOSL2's specific edge-selector syntax — a materially different interaction than the plain-primitive toolbar tools built in M4/M5, since "selecting an edge" isn't a concept `scene-graph` currently has (it only knows about whole nodes, not their sub-features), and (c) module-introspection (M8) needs to either special-case BOSL2 modules or generalize enough to toolbar-ify a third-party library, not just user-authored local modules. None of that is a natural fit inside an existing milestone's scope.

**Status**: not started. Promoted from stretch goal to v1 on 2026-10-16 (Jordan); sequenced after M11 and before the final Polish pass. Real edge-selection UX still wants a solid boolean/scene-graph foundation (M9) under it.

## Nested selection & drill-in navigation (M9)

Jordan asked (2026-09-15) whether the app could get something like a CAD timeline — scroll back to an earlier step, adjust it, have the change propagate forward to the current state. Two things came out of that conversation worth recording verbatim, since the conclusion ended up different from (and simpler than) the initial framing:

**Why "propagate forward" is already free, and a literal timeline isn't the right model.** OpenSCAD source is declarative, not stateful — every render already re-evaluates the *entire* file fresh from source (see "Bidirectional sync architecture" above), so editing an earlier statement and having it flow through to everything after it is the existing behavior today, for every edit, with zero extra plumbing. There's no dependency graph to build and no risk of the classic parametric-CAD failure mode where rolling back the timeline breaks a later feature that depended on something now-changed — that whole class of problem doesn't exist here. What a real CAD timeline actually provides beyond that is just (a) an ordered, navigable list of steps, and (b) the ability to edit an earlier one directly. So a literal chronological "history of actions" isn't what's missing.

**Why it's not literally a timeline either.** Jordan's own follow-up: if you paste in mostly-finished `.scad` source you wrote outside the app (or that came from someone else), there *is* no history of actions to scroll through — only whatever structure already exists in the source text. So "timeline" is the wrong mental model entirely for a tool that has to work equally well on freshly-authored and pasted-in code. The honest equivalent, and what this milestone actually is: **structural navigation** — drill into a nested block, treat its children as the current working set, edit one, then return to the full assembly via a breadcrumb. Not "when did I do this," just "where am I in the structure right now."

**What this actually requires**: `scene-graph.ts` currently models only **top-level statements** — a deliberately narrowed scope from M3 (see M3 build notes), where full per-nested-node isolation was explicitly deferred. Extending it to real nested children — inside a merged boolean block (M6), inside an extrusion's 2D children (M7), inside a custom module's own body (M8) — is the actual subsystem this milestone builds. The mechanism itself isn't new: M3 already isolates each top-level statement into its own render (source slice + context, independent `openscad-wasm` call, independent clickable mesh) — drill-in is the same mechanism applied one level deeper into the tree, plus a breadcrumb UI ("Assembly > Difference #2 > Cube") for the "return to the full picture" direction.

**Relationship to M6's pending boolean-children item**: M6's build notes already call out that a merged boolean's children become unselectable/undraggable once merged (see "Known limitations, intentionally deferred," M6 build notes) — a real regression M6 itself introduces (pre-merge, every shape is independently editable; post-merge, none of them are) that M6 needs some minimal fix for regardless of this milestone. That fix is the boolean-specific stopgap; this milestone is the generalized, permanent version — real nested-node modeling plus a proper breadcrumb/focus-mode UI, applied uniformly across booleans, extrusion children, and custom modules — so M6's fix is best understood as scoped narrowly enough to not block M6 itself, not as this milestone done early.

**Why sequenced M9 (after M8, before Polish)**: after M8 specifically, because by then every kind of nested/child content the app will ever produce (boolean children from M6, extrusion children from M7, module internals from M8) already exists — building drill-in earlier would mean solving it once for booleans and re-solving it again for each subsequent block type as it's added, rather than building the general mechanism once against the full set. Before Polish, because this is substantial, load-bearing interaction-model scope in its own right, not a polish-pass item — and the Polish backlog's other pending idea (the Onshape-style tool-first operation panel, below) would likely want this same breadcrumb/focus-mode affordance anyway, so drill-in existing first is the better order.

**Status**: done 2026-11-25 (scoped 2026-09-15). See "M9 build notes" below.

## Sketch mode (M7.5): plane-based parametric sketching

Scoped 2026-09-16 (with Jordan). This is the biggest single interaction subsystem in the plan after the core edit loop itself — a real CAD sketch workflow, deliberately split out of M7 so M7 can ship working extrusions (wrap an existing 2D primitive, edit its params) without blocking on it. M7 makes 2D profiles *exist and render*; M7.5 makes them *drawable and editable as sketches*.

**The target workflow** (Jordan's description, verbatim intent): pick a sketch plane — either a **global plane** through the origin (XY / XZ / YZ), or a plane derived from a **flat face of an existing solid** (click a face, sketch on it) — then draw a profile on that plane from **lines and points** (and realistically arcs/circles too), with the camera locked to look straight at the plane while sketching, then **extrude** the finished profile into a solid. This is the Onshape/Fusion/SolidWorks sketch→feature loop, which is *the* central modeling paradigm those tools are built around, adapted to emit plain OpenSCAD.

**Why it's genuinely its own milestone, not an extension of M7.** Four distinct pieces, none of which the app has any foundation for today:

1. **A custom camera / sketch-plane system.** Everything so far uses a single free-orbit `OrbitControls` camera (see Viewport.tsx). Sketch mode needs: a notion of an active plane (origin + normal + in-plane basis vectors); the ability to define that plane either from a global axis pair or from a picked face of an existing mesh (which requires face-level raycasting and extracting the face's plane — three.js raycast hits already carry a face normal, so the hit point + normal give the plane directly, but mapping that back to a *stable* SCAD-expressible transform, e.g. the `translate`/`rotate` that puts the sketch where the face is, is the real work); and a camera mode that animates to look orthographically straight down the plane normal and locks orbit while sketching (distinct from the free-orbit modeling camera — a real mode switch, with a clean way back out). This alone is comparable in scope to the M4-era gizmo/camera work.

2. **A 2D sketch-entity model that round-trips to SCAD.** Sketch geometry (points, line segments, arcs, closed loops) is a different data model from the current node/`module_instantiation` scene graph — it's sub-primitive. The honest SCAD target for a hand-drawn closed profile is `polygon(points=[...], paths=[...])` (arcs approximated to segments at some resolution, or emitted via a helper module), placed under the plane's `translate`/`rotate`. So M7.5 needs a sketch representation that (a) edits smoothly as points/lines in the viewport and (b) serializes to a `polygon()` (plus, ideally, parses one back *in*, so a sketch survives a reload — same "the .scad file is the source of truth, no sidecar" constraint the constraints layer already commits to). Whether a drawn rectangle emits a readable `square()` vs. a generic `polygon()`, and how much intent survives the round-trip, is a real design question to settle here.

   **OpenSCAD's native 2D toolkit** (surveyed 2026-09-17, ahead of implementation): primitives are `square`, `circle`, `polygon(points, paths)`, `text` (blocked here regardless — openscad-wasm's font gap). Notably **no native arc/line-segment primitive and no native fillet/round on a polygon's corner** — real OpenSCAD users fake arcs with a dense `polygon()` point list (or reach for BOSL2, M13's stretch scope) — so a sketch tool that lets someone draw an arc or a rounded corner has no clean 1:1 SCAD construct to emit; it's a point-dense `polygon()` approximation either way, same as hand-written OpenSCAD would produce. Two native 2D-relevant *operations* worth exposing as real sketch-mode toolbar ops rather than leaving to raw point editing: `offset(r | delta, chamfer)` (inset/outset a profile by a distance, square/round/chamfer corners) and `projection(cut)` (flattens a 3D shape to 2D — cross-section or silhouette; the natural way to seed a sketch from a picked face's outline, tying into point 1's face-plane picking). Both are first-class 2D→2D/3D→2D ops already, no new SCAD concepts needed.

3. **On-plane drag editing (the Stage-3 gizmo problem from M7's notes).** Dragging a sketch point or edge in the plane is a fundamentally different manipulator from the existing rigid-body `TransformControls` (which move/rotate/scale a whole object, never reshape one). This needs per-vertex/per-edge handles constrained to the sketch plane, converting an in-plane drag into an edit of the underlying `polygon` points — analogous to how the existing gizmo converts a world drag into a `translate([...])` edit, but at the point level, not the whole-shape level.

   **Constraints, tiered (decided 2026-09-16/17, with Jordan)**: real sketch tools (Onshape/Fusion/SolidWorks) universally have coincident/parallel/perpendicular/tangent/equal constraints plus dimensional ones — without them, dragging one point of a "rectangle" just makes an arbitrary quadrilateral, not a resized rectangle. Deliberately **not** building a second, sketch-only constraint solver for this. Two tiers instead: (a) **snap-while-drawing** — horizontal/vertical line snapping, endpoint-coincidence snapping, snap-to-existing-geometry — cheap, no solver, ships as part of M7.5 itself, covers most of the "why didn't my rectangle stay square" frustration by getting it right at draw-time; (b) **real parametric constraints that survive edits** (drag a point, dependent geometry stays valid) route through **M12's** existing solver-based-constraints work instead (`constraints/` package, DOF bookkeeping, `@constraint:` annotations) — sketch points/lines are the same DOF-solving problem M12 already exists to handle, just applied at the 2D-point level instead of whole-3D-object level, so this becomes M12 scope once M12 is actually built, not new M7.5 scope.

4. **The extrude hand-off.** Once a profile is drawn, "extrude it" wraps the sketch's `polygon()`/2D primitive in `linear_extrude`/`rotate_extrude` — which is exactly the M7 extrude tool, so this part *does* reuse M7. M7.5's job is producing a clean, selectable 2D profile for M7's extrude to consume; the two milestones meet here.

5. **Orientation navigation cube (raised by Jordan, 2026-09-16), plus a shading-mode dropdown.** A small fixed-position widget (top-right of the viewport, Fusion/SolidWorks/Onshape-style) showing a live-updating cube oriented to match the current camera — click a face to snap the camera to look straight at it (Front/Top/Right/...), click an edge or corner to snap to the corresponding 2-axis/3-axis diagonal view, small arrow glyphs around it to rotate view by fixed steps. A shading-mode dropdown (shaded / shaded-with-wireframe / wireframe-only) sits alongside it — unrelated to camera orientation itself but the same "fixed viewport-corner overlay" UI family, so grouped with it rather than becoming a separate floating control. This is **exactly the same underlying primitive sketch mode's plane-lock camera needs** (point 1, above): "smoothly animate the camera to look straight down a given direction/normal." A nav-cube click and "enter sketch mode on this face" are the same operation — animate-camera-to-orientation — just triggered from a fixed cube widget vs. a picked face's normal. Worth building the animate-to-orientation primitive once and driving both from it, rather than two independent camera-animation code paths.

**Dependencies / sequencing.** Depends on M7 (extrude tools + bare-2D-primitive rendering must exist first — a sketch you can't render or extrude is pointless). Strongly wants **M9 (drill-in navigation)** for the "enter the sketch, edit it, exit back to the assembly" mode transition — sketch mode *is* a drill-in focus mode with a specialized editor, so ideally M9's breadcrumb/focus-mode mechanism exists first rather than M7.5 inventing a parallel one. That argues for M7.5's *real* build slot being after M9 despite the number (the ".5" reflects topical adjacency to M7/extrusions, not literal build order — flagged here explicitly so a future reader doesn't take "7.5" as "build right after 7"). Face-based planes also lean on face-level selection, which overlaps conceptually with M13's (BOSL2) edge/face-selection needs — worth building the face-picking primitive once, reusably, whichever lands first.

The nav-cube + shading-mode piece (point 5) is the one exception to all of the above — it's a general-viewport improvement that works against the *existing* free-orbit camera and doesn't need a plane system, sketch-entity model, or drill-in navigation to be useful. It could ship any time as its own small slice, standalone, well before the rest of M7.5 — noted here rather than in the M10 UX backlog specifically because the camera-animation primitive it needs is the same one the rest of this milestone needs, so building it in isolation now would mean redoing that primitive later rather than sharing it.

**Status**: in progress, scoped 2026-09-16. Slices 1-3 shipped (2026-09-17/19/20/22, see build notes below): plane picking (global XY/XZ/YZ *and* face-based, with a locked camera for both), click-to-place point drawing → real `polygon()`, and the full extrude hand-off back into M7's tools — all verified end-to-end for every plane kind. Draw-time snapping shipped 2026-10-15 as slice 4 (grid, existing points/edges, alignment, close-the-loop; applies to point drags in an edited sketch too — see its build notes). On-plane editing shipped 2026-10-15 (see build notes below): "Edit Sketch" re-opens an already-committed sketch, bare or extruded, on the plane it was drawn on, with its points as draggable handles (drag to move, click near an edge to insert, double-click to delete, Undo), and saves back into the same `polygon()` in place. Still open: the sketch-entity model is points-only (no line/arc tooling beyond straight segments between clicked points), and one profile per sketch session. The nav-cube + shading-mode piece (point 5) shipped 2026-10-15 as its own slice (see build notes below), sharing one camera-animation primitive with the sketch-plane lock as planned.

## M10 UX/polish backlog (ongoing — append here as ideas come up)

M10 itself doesn't start until the earlier milestones (M0-M9) are done, but UI/usability ideas keep surfacing *while* building those — usually as "this works, but a real CAD tool would present it better" observations made in passing, not as their own milestone-sized detour at the time. Rather than losing them or scope-creeping them into whatever milestone happened to be in progress, they get written up here in full (the actual idea, why it's not just done immediately, and what it'd touch) and left for M10 itself to triage and scope for real. Each entry should be dated and stand alone — don't assume the reader has the conversation that prompted it.

**Onshape-style tool-first operation panel (raised by Jordan, 2026-09-15).** Currently, multi-target operations (so far, just M6's Union/Difference/Intersection) use a *selection-first* model: click shapes in the viewport (plain/ctrl/shift per the usual multi-select conventions), then click the operation button, and the operation infers roles from click order (difference()'s base is whichever shape was clicked first, the rest are the subtracted tool(s) — see M6 build notes). As of 2026-09-14's selection-modifier fix, the base vs. tool(s) distinction is at least visible in the viewport itself (base stays the amber "selected" color, tool(s) render in a second, distinct red, with a small color-key legend inline in the Boolean toolbar row — see App.tsx's Boolean toolbar group and Viewport.tsx's `SelectionRole`/`OPERAND_MESH_COLOR`). That's a real improvement over inferring roles from memory of click order, but it's still a *read-only* affordance bolted onto the selection-first model, not a real solve.

Onshape (and most real CAD tools) use the opposite model: *tool-first*. You click the operation you want (e.g. "Difference") before selecting anything, which opens a small floating panel with explicitly labeled slots ("Base", "Tool(s)"), each slot individually clickable/re-clickable to (re)assign which shape fills it, plus any of that operation's own parameters inline in the same panel (visible immediately, not requiring a separate parameter-panel context switch) — and only commits once you confirm. This generalizes far better than click-order inference: it reads correctly even if you select in the "wrong" order, it scales to operations needing more than two role-slots or non-boolean parameters (M7's extrude distance, M11's constraint targets, M13's BOSL2 edge/face selectors), and it's self-documenting in the moment rather than relying on a legend the user has to already know to look for. It would also likely want the same breadcrumb/focus-mode affordance M9 (drill-in navigation, above) builds, rather than inventing its own.

**Why not just build it now**: this is a real interaction-model change, not a small tweak — it needs (a) a new floating-panel UI component (positioning near the relevant geometry, not just another toolbar row — this is the same "floating panel" affordance the M5 parameter panel already wants, per the pre-existing 2026-09-11 note below, so the two should probably share one mechanism rather than becoming two different floating-panel implementations), (b) a *tool-first* selection state machine living alongside (not replacing — plain single-object selection for the gizmo/parameter-panel/mirror/color workflows is still selection-first and should stay that way) the current selection-first one, and (c) is worth designing once as a general "operation panel" pattern before M7/M11/M13 each need their own version of the same problem, rather than bolting a one-off onto just the boolean toolbar today. Real scope, not urgent — hence M10, not now.

**Gizmo drags a single-variable axis (decided by Jordan, 2026-11-26, for M10, listed under M10d; superseded the same day: built in M11 as linked drag, see the M11 build notes).** In M11 a translate axis written as an expression is locked (decision 8), including one that is a single variable, as Distance/Align with "Follow changes" leaves the reference part (`translate([cube_x, 0, 0])`). In M10: when the axis is exactly one top-level variable assigned once to a plain number, and the part reads that variable (not a same-named module parameter or loop variable), dragging that axis rewrites the variable's number, so every part that reads it moves too (a followed part comes along, like a mated part in Onshape). While dragging, the Position note says "Dragging edits cube_x (used in N places)", since the variable may also be used elsewhere, e.g. as a size. Typing a plain number into Position still detaches the axis. Any other expression axis stays locked. Sketch of the change: `gizmoAxes()` takes the free axes and returns them as `driven`; `handleTransformCommit` re-parses the patched source and sets the variable.

**Face picking and dimension lines for Distance (decided by Jordan, 2026-11-26; M10d).** M11's Distance/Align pick a plane on each part's axis-aligned box with axis and min/center/max buttons, and show only a text preview. Jordan's model is Onshape's sketch dimensions: click a face/edge/line on each part and see a dimension line between them. The item: (1) click a flat face in the 3D view; if it lines up with X, Y or Z it maps to that part's min or max on that axis (a curved part snaps to its tangent plane or center; faces at other angles are refused, since one translate value can't hold them); (2) draw a dimension line with its value between the two faces, while placing and whenever either part is selected, and click the number to edit the gap (reading the dimension back from the expression the tool wrote); (3) built into the M10 floating tool windows. Distance/Align are marked experimental in beta-v0.1.6; see the M11 build notes on revisiting them with the solver.

**Floating parameter panel (Jordan's suggestion, 2026-09-11).** Move the M5 parameter panel out of its current toolbar row and into a floating panel anchored near the selected object in the viewport — more Onshape-like, and reads its own context (which object, which args) from proximity instead of needing the `callName` label the toolbar row currently spells out. Likely shares a mechanism with the operation panel above (both are "floating, anchored-to-geometry panels"), so worth scoping together rather than as two independent UI components.

**Tool panels float over the viewport (decided by Jordan, 2026-11-25, after M11; M10b).** M11 shipped its Distance / Align / Pattern panel as a docked strip under the toolbar, with the Pattern count/spacing strip and the Make variable prompt beside it. In the M10 UI rework these become floating windows over the 3D viewport, like Onshape's feature dialogs: a titled window in the viewport's top-left area with the labeled part slots (Move / Relative to, Part), the tool's own fields, the preview and Apply/Cancel, so the model stays in view while you pick. Scope it together with the two entries above (tool-first operation panel and floating parameter panel) as one floating-window component that the booleans, extrudes, M11 tools, Text and M13's edge tools all use. It also clears the toolbar wrap noted in "M11 build notes" (three rows at 1280 px). Open for M10 to settle: whether windows can be dragged, whether position is remembered, and how one window yields when another tool starts.

**Render progress and stale-render indication (raised by Jordan, 2026-11-26).** Opening the gag trophy (`apps/desktop/test/fixtures/gag_trophy1.scad`, about 75 s per render) kept the previous document's model in the viewport for the whole render, with only the small "Rendering..." text at the right end of the top bar to say anything was happening. Not a bug in the sense of broken code, but not a deliberate design either: `runRender` in `App.tsx` renders every node of the working set and only then calls `setNodeMeshes`, so the old meshes stay up until the new set is complete, and the only signal is `setStatus('Rendering...')`. There is no per-node progress, no elapsed time, and no way to cancel. Per-node progress alone would not help this file: its top level is variables, module definitions and one `if (part == ...)` chain, so the whole model is a single node and a single ~75 s engine call. What M10 should do:
- *Stale indication*: while a render is in flight, mark the viewport as out of date (dim or desaturate the old meshes, plus a "Rendering..." overlay on the viewport itself, not only in the top bar). On opening a different file, clear the previous document's meshes at once rather than showing them under the new file's name.
- *Progress*: an indeterminate progress bar with elapsed time for a single long engine call, and "node 3 of 8" when the working set has several nodes. The engine has no percentage output for Manifold renders, but it does print stage lines ("Parsing design", "Compiling design", "Rendering Polygon Mesh using Manifold..."); forwarding those from `renderWorker.ts` through `renderHost.ts` to the renderer would give a real stage label.
- *Cancel*: a Cancel button that kills the render process (`renderHost.kill()` already exists and the next render starts a fresh process), so a long render started by mistake does not have to be waited out.
- Worth checking at the same time why this file takes ~75 s here and how long OpenSCAD's own F6 takes on the same machine, in case part of it is the engine build rather than the model.

**True model colors, with a highlight on selection and hover (raised by Jordan, 2026-11-26).** The gag trophy renders entirely in the default blue, while OpenSCAD shows its colors (`color("goldenrod")`, `color("saddlebrown")`, `color([0.15, 0.15, 0.15])`, ...). Not intended. Two causes, both in the current design:
1. *Renders export binary STL* (`--export-format=binstl` in `scadRender.ts`), which has no color, so any `color()` below the node's own outer wrap is lost. In this file every `color()` is inside the `assembly()` and `key_assembled()` modules, and the whole model is one node, so none survive.
2. *The only color the viewport knows is the node's outer `color()` wrap*, read by `decomposeNode` in `targetedPatch.ts` and applied as one material color per mesh in `Viewport.tsx`. `readVectorCall` only accepts a vector literal, so a named color (`color("red")`) or a hex string (`color("#ff0000")`) is not read even there; the mesh falls back to `DEFAULT_MESH_COLOR`.

On top of that, selection *replaces* the mesh color with amber (`SELECTED_MESH_COLOR`; boolean operands red, `#` purple), so even a correctly colored node loses its color while selected. There is no hover highlight on meshes.

Checked 2026-11-26 against the bundled engine (`@lofcz/openscad-wasm` 0.0.2): `--export-format=off` writes per-face RGB, and it survives modules and booleans. A test file with `color("goldenrod")` and `color([0.1,0.2,0.9])` inside a module, an uncolored cube, and `difference() { color("red") cube(8); color("green") ... }` came out as 218,165,32 (goldenrod), 25,51,229, 255,0,0 for the base, 0,128,0 on the faces the green cutter made (the same thing OpenSCAD's own render shows), and 249,215,44 (OpenSCAD's default face color) for the uncolored cube. 3MF export also works and carries colors, but is a zip and heavier to parse. What M10 should do:
- Switch the isolated renders from binary STL to OFF (or another format with face colors), parse per-face colors into a vertex-color attribute in three.js, and keep the node's outer `color()` wrap as an override, the way it works now for the color picker. Map the engine's default face color to the app's own default so uncolored parts still look like today. Measure parse time and size against STL on the module-heavy fixtures; OFF is text, so large meshes may need a fast parser.
- Read named and hex colors in `decomposeNode` too (OpenSCAD's named color list is the SVG/CSS one), so the color picker shows the right color and editing it round-trips.
- Show selection and hover as a *highlight over* the real colors (an outline or edge glow, or a light tint, plus a distinct hover state), not a replacement color. Boolean base/tool roles and the `#` modifier need the same treatment, and the color-key legend in the Boolean toolbar should match whatever is chosen. Alpha from `color([r,g,b,a])` should keep working.
- The dimmed context meshes when drilled in (M9) can stay grey, or become a faded version of their real colors; decide when building.

## Where the build diverges from this plan (updated 2026-11-22 after the QC audit fixes)

Found in a review of this plan against the code, refreshed by the 2026-11-22 QC audit. None of these is a bug; they are places where the plan describes a design the code never adopted. Whether to adopt it later is an open question for Jordan.

Fixed by the 2026-11-22 QC fix PR, listed so the history is clear: renders now pass `--backend=Manifold` (they had silently used CGAL, about 57x slower); visual edits go through Monaco `executeEdits` so they are undoable (they used `setValue`, which wiped undo); `use`/`include` files are copied into the WASM filesystem so imports resolve; Save / Save As with an unsaved-changes prompt exists ahead of M10.

- **One app, not `packages/`.** The code is a single Electron app in `apps/desktop` (about 4,600 lines as of 2026-11-22): `sceneGraph.ts`, `targetedPatch.ts`, `scadParser.ts`, `primitives.ts`, `coalescingRunner.ts` and two components. The package split (`scad-cst`, `scad-ast`, `scad-codegen`, `scene-graph`, ...) was never made. The "Package boundaries" section above is the original intent, not the current layout.
- **Rendering runs in a dedicated Electron utility process** (`src/main/renderWorker.ts`, managed by `renderHost.ts`), not a renderer Web Worker. M1 ran OpenSCAD synchronously in the main process; on 2026-11-25 a detailed model (`apps/desktop/test/fixtures/gag_trophy1.scad`, ~75 s and ~1.5 GB per render) froze every window for the whole render and could take the app down, so rendering moved out. If the render process dies, that render fails with a message and the next one starts a fresh process; renders export binary STL.
- **Tests arrived late.** The plan calls for unit tests of the patch engine in CI from M3; a Vitest unit and integration suite (`apps/desktop/test`) was only added on 2026-11-22. Earlier milestones were verified manually in the running app.
- **No Zustand store.** UI, selection and the parsed tree live in React state and refs in `App.tsx`, not in a separate store.
- **Raw `monaco-editor`**, not `@monaco-editor/react`.
- **The engine is bundled from `node_modules`** (inside `app.asar`, its `.wasm` unpacked), not shipped as loose `extraResources`. Since M15 (2026-11-25) it is `@lofcz/openscad-wasm`, not `openscad-wasm`; see "M15 build notes". The bundled fonts also come from that package rather than loose files.
- **Parsing is not incremental.** Each edit re-parses the whole document with the loaded parser (fast enough so far); `tree.edit()` is not wired in.
- **Selection is positional within a working set**, carried across edits by text matching (`nodeIdentity.ts`, M9) rather than the stable-ID fingerprinting the architecture describes.
- **Nested nodes are reached by drilling in** (M9): the scene graph is still one level at a time (the top level, or the children of the drilled-into node), not one tree of every nested node.

## Critical first files

- `packages/scad-cst/src/index.ts` — grammar loading + incremental parse/edit API; foundation everything depends on.
- `packages/scad-ast/src/nodes.ts` — typed semantic AST node definitions.
- `packages/scad-codegen/src/targetedPatch.ts` — minimal-diff text-patching engine; gates both sync (M2-M4) and toolbar insertion (M5+); needs strong test coverage (round-trip: parse → patch → reparse → assert semantic equivalence + "only intended byte range changed").

## Risks to flag explicitly (not blockers, but track)

1. **Grammar completeness** — tree-sitter-openscad is small/active but not battle-tested at scale; M0 must stress-test real-world files (list comprehensions, `let()`, `each`, string escapes) before committing further milestones.
2. **WASM render latency at scale** — N+1 invocations per edit even with caching/debouncing could lag for large assemblies; the "skip WASM for rigid-transform drags" optimization may need to become mandatory, not optional, pending M0/M3 benchmarks.
3. **Electron WASM/CSP setup** — may need explicit `wasm-unsafe-eval` CSP allowance; if Manifold's WASM build uses threads/SharedArrayBuffer, cross-origin-isolation headers need configuring for Electron's local-file serving — validate in M0, not at packaging time.
4. **Structural-edit codegen correctness** — brace-insertion/indentation-inference for wrap-in-boolean and insert-at-selection is inherently more failure-prone than simple value replacement; needs solid property-based round-trip tests in `scad-codegen`.
5. **Node-identity heuristic isn't provable** — pathological edits (duplicate/reordered identical statements) could cause a selection/gizmo to "jump" to the wrong node; mitigate with a visible confirm-flash on the still-selected node after any external text edit, rather than assuming the fingerprint heuristic is perfect.
6. **`include`-sourced modules for the toolbar** — since `include` executes side effects, aggressively toolbar-ifying modules pulled in via `include` (vs. `use`) risks surfacing modules whose behavior implicitly depends on including-file state; document as a v1 limitation, recommend `use` for tool libraries.
7. **GPL licensing** — OpenSCAD is GPLv2+, and its WASM build inherits that; bundling it inside the Electron app has real distribution/compliance implications that are a licensing/business decision, not a technical one — needs sign-off before shipping, independent of the technical plan. **Decided 2026-11-22: GPL-3.0-or-later** (LICENSE in the repo root). The WASM build includes GPLv3+ CGAL, so GPLv3 is the license that fits what ships.

## M0 spike results (2026-09-02)

Ran the M0 de-risking spike (`spikes/` in this repo: `npm run spike:parse`, `spike:render`, `spike:gaps`) against `web-tree-sitter@0.25.3` + `@holistic-stack/tree-sitter-openscad@0.1.0` (ships a prebuilt `tree-sitter-openscad.wasm`, no local emscripten/docker toolchain needed) and `openscad-wasm@0.0.4` (npm, Emscripten build with the WASM binary embedded as base64 in a single ~14MB `openscad.js`, works directly in plain Node — no Electron needed to validate the engine itself).

**Go decision: proceed with this stack.** 6 of 7 hand-written fixtures (covering primitives, transforms, booleans, extrusions, modifiers `# % ! *`, modules/functions, `use <file>` resolution, string escapes, basic list comprehensions/ranges/`let()`/`if`-filters) parsed with zero grammar errors and rendered to valid non-degenerate STL via openscad-wasm. Tree-sitter's error recovery is confirmed local/isolated — a bad construct on one line does not break parsing of the rest of the file, which validates the planned "keep showing last-known-good mesh for affected nodes only" sync behavior (section: Bidirectional sync architecture).

**Two confirmed grammar gaps** (isolated via `spikes/isolate-gaps.mjs`, cross-checked against openscad-wasm as ground truth — both constructs compile and render fine in real OpenSCAD, so these are genuine tree-sitter-openscad gaps, not invalid fixtures):
1. Bare `each` as a direct list-literal element outside a `for` comprehension: `[each [1,2,3], each [4,5], 6]` → ERROR. (`each` *inside* a `for` comprehension, e.g. `[for (v = [1,2,3]) each [v]]`, works fine.)
2. Chained/nested `for` clauses in one comprehension: `[for (x=[0:2]) for (y=[0:2]) [x,y]]` → ERROR. (The combined multi-variable form `[for (x=[0:2], y=[0:2]) [x,y]]` works fine.)

Both are narrow, real OpenSCAD features but not core to primitives/transforms/booleans/extrusions MVP scope. Treat as known-unsupported syntax for now: such statements will show as an error-recovery ERROR node in the scene-graph (last-known-good mesh retained, per the sync design) rather than blocking the rest of the file. Since the grammar is MIT-licensed and actively maintained, consider upstreaming a fix once the app's own priorities allow it, and re-run `spike:gaps` after any grammar version bump to check if either has been fixed.

**Two engine-integration findings that change the render-worker design**:
1. **A single `createOpenSCAD()` instance cannot be reused across multiple `renderToStl()` calls** — the second call on a reused instance throws (state corruption in the Emscripten module, likely virtual-FS/global state not resetting). Confirmed: a fresh instance per render call works reliably. Since the planned per-node isolated-render strategy already implies many render calls per document, `render-worker` must create a fresh `createOpenSCAD()` instance per render job (or find/implement a reset hook) — this is not an optional optimization, it's required for correctness. **New risk to track**: instance creation cost (parsing/instantiating a ~14MB WASM module) per isolated-node render may be a bigger performance concern than raw CSG time — needs benchmarking before M3, and may push the "special-case pure rigid-transform drags to skip WASM" optimization (already in the per-node selection section) from "nice to have" to "required for usable drag latency."
2. **`addFonts`/`addMCAD` are declared in this package's TypeScript types but not actually implemented/exported** by `openscad-wasm@0.0.4`'s bundle (only `createOpenSCAD` is exported) — `text()` calls fail with a Fontconfig error since no font assets are registered. MCAD library support is similarly unavailable out of the box. This is a real gap versus the plan's assumption of using this package as-is for fonts/MCAD; options to revisit before M7/M8 (extrusions/custom-modules milestones, where `text()` support would matter): build `openscad-wasm` from source with font assets bundled, evaluate `openscad-wasm-prebuilt` (a different npm package) or the openscad-playground project's own build for a version with working font support, or ship without `text()` in early milestones and treat it as a deferred primitive.

## Known engine bug: linear_extrude(twist=...) + low $fn crashes WASM (2026-09-07)

Found while building a manual test/demo file (`spikes/fixtures/test-drive.scad`): `linear_extrude(height=h, twist=..., slices=...)` applied to a `circle()` with a **low polygon count** (`$fn=6`, `$fn=7`, `$fn=10` reproduced; `$fn=8`, `12`, `16`, `20`, `32` all fine — not a clean "below N" threshold) crashes `openscad-wasm` with a hard `RuntimeError: null function or function signature mismatch`. This is a genuine WASM-level fault (an Emscripten indirect-call-table error), not a normal OpenSCAD compile error — it propagates as an unhandled main-process exception, not a graceful "render failed" the way invalid syntax does. Reproduced in complete isolation (fresh process per test case, ruling out cross-call contamination) via a throwaway `spikes/isolate-crash.mjs` (not committed — one-off repro, not a reusable fixture like `bench-*.mjs`).

**Update 2026-11-25**: renders now run in their own process (see "Where the build diverges" above), so an engine fault like this one fails that render with a message instead of reaching the main process.

**Why this matters going forward**: this is exactly the kind of input the M5 toolbar (extrude tool) or a user typing a low-poly twisted extrude could trigger, and right now it would surface as an ugly generic IPC error rather than anything resembling OpenSCAD's own error reporting. Worth a defensive check (e.g. clamp/warn on very low `$fn` specifically when `twist` is also set) before M5/M7 ship an extrude tool, rather than passing arbitrary user `$fn` values straight through. For now, just avoid the combination in example/demo content.

## Render latency benchmark (2026-09-03, ahead of M2)

Before building M2's live-sync loop, benchmarked `openscad-wasm` render cost (`spikes/bench-render.mjs`, `spikes/bench-isolate.mjs`) since M2's whole point is a responsive editing feel and this was previously unmeasured.

**Good news for the per-node isolated-render strategy (M3+)**: individual constructs rendered in isolation are cheap — a boolean difference is ~18ms, a union with a tessellated cylinder ~163ms, even the most expensive single construct tested (sphere∩cube intersection) was ~264ms. Fresh-instance overhead (the M0 finding that instances can't be reused) is negligible after the first call in a process (~25-40ms steady state, down from ~130ms cold) thanks to V8's WASM module-compile caching on identical bytes.

**Real finding that changes M2's implementation, not just a number to note**: rendering a full document with several *separate top-level statements* (as OpenSCAD implicitly unions all top-level siblings into one final result) costs far more than the sum of its parts — `spikes/fixtures/basics.scad` (5 sibling top-level statements: a union, an intersection, a transform chain, a linear_extrude, a rotate_extrude) took **~1.2s steady-state**, vs. ~460ms if you summed each construct's isolated cost. This is inherent to CSG boolean cost scaling with combined complexity, not a bug — but it means a naive "fire a full-document render on every debounced text change" loop can produce overlapping ~1.2s renders if the user keeps typing through a debounce window, since Electron's main process executes JS/WASM on one thread and concurrent `openscad-wasm` calls contend for the same CPU rather than running in parallel.

**Mitigation implemented in M2**: the render trigger isn't a naive "one render per debounce tick." It's a coalescing queue — at most one render in flight at a time; if new text arrives while a render is running, only the *latest* text is kept and rendered next (any intermediate versions are dropped), rather than queuing every keystroke's render. This directly validates (not just theoretically motivates) the plan's existing two-tier fast-preview/full-render design and the render-worker's planned job-queue-with-cancellation — both were already in the architecture, this benchmark is why they're load-bearing rather than nice-to-haves.

## M2 build notes (2026-09-03)

M2 (live text→visual sync) is done: Monaco is now editable, `apps/desktop` bundles the real `web-tree-sitter` + `tree-sitter-openscad` grammar from the M0 spike (WASM assets copied into `src/renderer/public/`, loaded via `Parser.init` + `Language.load` in a new `scadParser.ts`), and every edit runs incremental parsing plus a debounced (400ms), coalescing-queued re-render (`coalescingRunner.ts`: at most one render in flight, latest text always wins — the mitigation the render latency benchmark above showed was necessary, not optional).

**Verified with a real simulated edit, not just a rebuild-and-look**: added a small, intentionally-kept manual-verification hook (`window.__testEditor`, driven by a `SCADSTUDIO_TEST_EDIT` env var in `main/index.ts` that scripts an edit via `executeJavaScript` before the existing `SCADSTUDIO_SCREENSHOT` capture) to actually exercise the live-edit path end-to-end under Xvfb: changed the cylinder's radius/`$fn` mid-session and confirmed the viewport updated to the new hexagonal-prism geometry, matching the edited source exactly. Separately fed intentionally broken syntax (unbalanced parens) and confirmed graceful degradation: the status bar shows `"1 parse error(s) — Render failed: ..."`, the app doesn't crash, and — as an emergent property of simply not overwriting state on failure, not a deliberate feature yet — the viewport keeps showing the last successful mesh instead of going blank. That's the scene-graph's planned "last-known-good mesh" behavior showing up naturally before the scene-graph itself exists.

**Real bug found and fixed**: the WASM assets (`tree-sitter.wasm`, `tree-sitter-openscad.wasm`) were referenced with a leading-slash absolute path (`/tree-sitter.wasm`), which resolves against the OS filesystem root — not the app bundle — once packaged and loaded via `win.loadFile()` (`file://` protocol), as opposed to Vite's dev server (`http://localhost`) where it happened to work. Fixed by routing through `import.meta.env.BASE_URL` (Vite's documented convention for referencing `public/` assets in a base-aware way), so the same code resolves correctly in both dev and the packaged file:// build.

**Risk #3 confirmed, not just theoretical**: WebAssembly instantiation in the renderer failed outright under the M1-tightened CSP (`script-src 'self'`) with `CompileError: ... violates ... because 'unsafe-eval' is not an allowed source`. Fixed with the narrower `'wasm-unsafe-eval'` CSP source (not the broader `'unsafe-eval'`) — Chromium's dedicated, more secure directive for exactly this case. This is the plan's already-flagged CSP risk, now confirmed real and resolved with the precise fix rather than reopening full eval.

**Known rough edge, not yet fixed**: a failed render (e.g. from broken syntax) surfaces as a generic `[object Object]` IPC error string rather than OpenSCAD's actual stderr message, because the main process's `ipcMain.handle` rejection serializes the raw error oddly across the IPC boundary. Since M2 has no per-node error attribution yet (that's M3's scene-graph), a nicer error surface isn't worth building now — revisit when wiring real diagnostics in M3+.

## M3 build notes (2026-09-04)

M3 (scene-graph + click-to-select) is done, with a deliberately narrowed scope: `sceneGraph.ts` derives a flat list of **top-level statements only** (not the full nested-node tree the architecture describes) from the tree-sitter CST, isolates each one into its own `openscad-wasm` render call (source slice + all top-level definitions/assignments/`use`/`include` prepended as context), and the viewport renders each as its own clickable mesh. Clicking a mesh highlights the corresponding source range in Monaco (a decoration, not a cursor move, so it doesn't fight with active editing); clicking/moving the cursor in the text does the reverse. This is the plan's "first bidirectional selection milestone" — full per-nested-node isolation (e.g. selecting an individual child of a `difference()`) and the two-layer selection/display mesh split are explicitly deferred; every top-level statement here is self-contained enough that rendering it directly as the visible mesh is already correct, not just a selection-layer stand-in.

**Verified with real simulated interaction, not just a rebuild-and-look**: extended the existing `SCADSTUDIO_SCREENSHOT` test hook with two new env vars — `SCADSTUDIO_EXEC_JS` (runs arbitrary JS via `executeJavaScript`, used here to call `window.__testEditor.setPosition(...)`) and `SCADSTUDIO_CLICK_AT` (sends a **real** `mouseDown`/`mouseUp` pair via `webContents.sendInputEvent`, exercising the actual Chromium input pipeline → DOM → react-three-fiber raycasting path, not a JS shortcut around it). Confirmed both directions under Xvfb: setting the cursor inside the `sphere(r=8);` line turned the sphere orange in the viewport; a real simulated mouse click on the cylinder mesh highlighted lines 12-13 in the editor. Both hooks are kept (like the earlier ones) since they'll keep being useful for M4's gizmo-drag verification.

**Real bug found and fixed — a supertype-wrapping gotcha, not a logic error**: the scene graph initially misclassified every top-level statement as a geometry node (reporting "2/4 nodes rendered" for a file with only 3 real geometry statements, with the first two erroring out). Root cause: `tree-sitter-openscad`'s `source_file` node doesn't expose its children as their concrete type directly — every child is wrapped in a generic `statement` supertype node (visible in the tree, not hidden), and the classification code was comparing `child.type` (always `"statement"`) against concrete type names like `module_definition` that could never match. Fixed by unwrapping one level (`child.child(0).type`) for classification while still using the outer node's byte range for slicing. Worth remembering for `scad-ast` in later milestones: **this grammar's supertype nodes are real, visible tree nodes you must unwrap, not a hidden implementation detail tree-sitter flattens for you.**

**Unrelated tooling bug found and fixed along the way**: running `tsc --build` on the app's TS project references (added to actually typecheck, since `electron-vite build`'s esbuild/rollup pipeline strips types without full checking) silently overwrote the hand-written `src/preload/index.d.ts` global-augmentation file with a generated declaration, because `composite: true` projects emit output next to source when no `outDir` is set. Restored the file from git and added explicit `outDir`s (`.tsbuild/desktop-{node,web}`, gitignored) to both `tsconfig.node.json` and `tsconfig.web.json` so this can't happen again. Also hit React 19's `@types/react` moving the `JSX` namespace under `React.JSX` (no longer a bare global) — fixed by dropping the now-unnecessary explicit `: JSX.Element` return-type annotations rather than fighting the types module by module. A `typecheck` script was added to `apps/desktop/package.json` so this runs on demand going forward.

**Known limitation, intentionally deferred**: node "identity" is purely positional (`SceneNode.index`, recomputed fresh on every parse) — there's no stable-ID fingerprinting yet (that's explicitly a later-milestone concern in the architecture, needed once drag-editing requires selection to survive structural edits elsewhere in the file). For now, if the node count shrinks below the previously-selected index, selection is simply cleared rather than guessing at a remapped target.

## M4 build notes (2026-09-07)

M4 (translate gizmo) is done: dragging a selected shape's gizmo now patches its `translate([x, y, z])` arguments directly in the source, through the same targeted-patch philosophy the architecture doc calls for. New `targetedPatch.ts` (`findTranslateVector` + `patchTranslate`) covers both shapes: if the selected top-level statement is already `translate(...)`-wrapped, only the vector literal's byte range is replaced (`existing.xyz + delta`, reformatted); if it's bare geometry with no wrap (e.g. `bracket(30, 15, 4);`), a new `translate([...])` call is inserted immediately before it as a pure insertion. Both are minimal edits — nothing else in the file is touched, confirmed by inspecting the patched source directly (module definitions, sibling nodes, and formatting all survived untouched in both cases).

**Real bug found and fixed — gizmo attached to the wrong pivot**: `openscad-wasm` bakes every node's *absolute* position into its STL vertices (there's no separate transform channel it could use instead), so a mesh's own `Object3D.position` is always `(0,0,0)` — the coordinate origin, not the shape. Attaching `<TransformControls>` directly to that mesh (the first attempt) drew the gizmo at the OpenSCAD scene's coordinate origin rather than on the shape, since TransformControls always visualizes the target's own transform, never its geometry bounds. Fixed by wrapping each mesh in a pivot `<group>` positioned at the geometry's own bounding-box center, with the mesh offset by `-center` inside it (net-zero visual change); the gizmo now attaches to the group, and dragging it drags the visible mesh along for free via ordinary Three.js parenting — no manual position-syncing code needed. Verified by logging `group.getWorldPosition()` and independently hand-computing the expected value from `<Center>`'s combined-bounding-box recentering offset; they matched to 4 significant figures, which is what confirmed this was a real fix rather than a lucky-looking screenshot.

**Second real bug found and fixed — camera zoom-out on drag commit**: with the gizmo nested inside `<Bounds fit clip observe><Center>{...}</Center></Bounds>` (the same wrapper the node meshes live in), committing a drag caused the camera to zoom out until the shapes were nearly invisible against a now-tiny-looking grid. Cause: `Bounds` measures the combined bounding box of everything in its React subtree to fit the camera, and `TransformControls` internally adds its own helper objects to the scene (including a large invisible plane used for drag raycasting) as part of that subtree — `Bounds` was refitting the camera to include that plane, not just the real geometry. Fixed by lifting the gizmo out to be a sibling of `<Bounds>` at the `Canvas` level instead of nesting it per-node: each `NodeModel` reports its pivot group up via an `onGroupRef(index, group)` callback into a `Map` held in `Viewport`, and a single `<TransformControls>` is rendered outside `<Bounds>` targeting whichever group corresponds to `selectedIndex`. This is also a cleaner shape than the original per-node-conditional-gizmo approach (exactly one `TransformControls` instance ever exists, not one conditionally mounted per node).

**Verified with a real simulated drag, not a synthetic value change**: extended the `SCADSTUDIO_SCREENSHOT` test hook with `SCADSTUDIO_DRAG_AT` (`"x1,y1,x2,y2"`) — a real `mouseDown` → several `mouseMove` steps → `mouseUp` sequence via `webContents.sendInputEvent`, exercising the same Chromium input pipeline `SCADSTUDIO_CLICK_AT` already used for M3, extended to cover continuous pointer movement rather than a single down/up pair at one point. Confirmed under Xvfb, driving the actual on-screen gizmo handles (not calling drag handlers from JS): dragging the sphere's translate gizmo along its red (X) handle turned `translate([40, 0, 0])` into `translate([47.956, 0, 0])` — matching the simulated screen-space drag distance — with the bracket module definition and cylinder statement byte-for-byte unchanged; dragging the *unwrapped* `bracket(30, 15, 4);` node inserted a brand new `translate([8.869, 0, 0])` wrap above it, leaving every other line untouched. Both nodes visibly moved to the new position in the viewport after the debounced re-render landed. Pixel-coordinate calibration for the gizmo handles has to come from an actual screenshot each time (cropped/zoomed for precision) — camera framing shifts between builds enough that hardcoded coordinates from a previous run aren't reliable.

**Known limitation, intentionally deferred**: only the translate gizmo exists (rotate/scale/mirror are M5). The "skip WASM entirely during drag" optimization the architecture calls for is already implicit rather than explicit — dragging only ever moves the pivot group's live `Object3D` transform (no re-render fires until `onMouseUp`), so there's nothing extra to build for that part of M4's goal; a real per-frame WASM-skip mechanism only becomes meaningful once continuous visual feedback needs to reflect something WASM would otherwise compute (e.g. boolean previews in M6).

## M5 build notes (2026-09-07)

M5 is done for its two "prove it works" pieces — full transform gizmo set (rotate/scale, alongside M4's translate) and toolbar primitive insertion (cube/sphere/cylinder/square/circle) — with parameter panels explicitly deferred (see "Known limitation" below).

**Rotate/scale needed different find/insert rules than translate, not just a different mode string.** Translate is a world-space move, so `findTranslateVector` stays outermost-call-only (unchanged from M4) — patching a translate nested inside a rotate would apply a world-space delta in the rotated local frame, silently moving the shape wrong. Rotate/scale are "in place" edits instead: `targetedPatch.ts` gained `getLocalChain` (skips at most one leading outer `translate(...)`, then walks the `<call>(...) <body>;` chain inward) so a fresh `rotate`/`scale` wrap inserts immediately before the base primitive — `translate([40,0,0]) rotate([..]) sphere();` spins the sphere in place instead of orbiting it around the world origin. Verified concretely: rotating a translated sphere by -95° left it visually exactly where it was (sphere is symmetric, so any wrong composition would have swung it to an entirely different spot); scaling it 3.245x along one axis visibly stretched it into an ellipsoid at its own location, not at the origin.

**Gizmo mode wiring**: `Viewport`'s `TransformControls` now takes a `mode` prop (`translate`/`rotate`/`scale`) toggled by three toolbar buttons in `App.tsx`. Translate/rotate read the drag as `end - start` (position, then radians→degrees); scale reads `end / start` as a multiplicative ratio, since three.js's scale gizmo always operates on the *current* scale rather than an absolute value — composing multiple scale drags this way was verified to accumulate correctly onto the source's existing `scale([...])` (two drags of 3.245x then ~7.24x landed at 23.499x in one patched line, not two).

**Real bug found and fixed — negative numbers weren't recognized as existing wraps.** `-95.406` doesn't parse as a `number` node in this grammar; it's a `unary_expression` (`unary_minus_operator` + `number` operand). `readVectorCall` only accepted bare `number` nodes, so any existing `translate`/`rotate`/`scale` with a negative component silently failed to be found — `findLocalTransform`/`findTranslateVector` reported "no existing wrap," and a second drag inserted a *duplicate* wrap next to the first instead of patching it (caught by dragging the same rotate twice: got two nested `rotate(...)` calls instead of one combined value). This affected M4's translate too, in retrospect — M4's verification runs just never happened to end up with a negative coordinate. Fixed with a `readNumber` helper that also unwraps `unary_expression` via its `operand`/`operator` fields.

**Real bug found and fixed — a gizmo commit could silently deselect its own node.** Every commit flows the patched source back into Monaco via `model.setValue()` (so the editor reflects the edit) — Monaco resets the cursor to the document start as a side effect of a full-buffer replace, which fired `onDidChangeCursorPosition` with reason `ContentFlush`, which `Editor.tsx`'s text→selection handler treated as "the user clicked at offset 0" (inside the leading comment, no scene node there) and deselected. The async render's own selection-preserving logic then ran *after* this and found the already-nulled selection, "preserving" nothing. Symptom looked mode-specific (only reproduced reliably on rotate) purely because of a race — it's a general bug, not particular to rotate. Fixed by ignoring cursor-position-changed events with `reason === monaco.editor.CursorChangeReason.ContentFlush` in `Editor.tsx`. Also hardened `Viewport`'s `onPointerMissed` with an `isTransformingRef` guard (deferred via `setTimeout(0)` past the native `click` that follows a `mouseup`) as defense-in-depth against a related but narrower case: a very small drag landing just past a thin gizmo ring's hit area.

**Verified with real simulated drags throughout**, extending the same `sendInputEvent`-based hooks from M3/M4: `SCADSTUDIO_CLICK_AT` and `SCADSTUDIO_DRAG_AT` now both accept `;`-separated sequences (click a mode button, then select a shape, then chain multiple drags on the same gizmo) rather than a single action per launch — needed to exercise "commit, then drag the same gizmo again" within one process, since app state doesn't persist across launches. Pixel calibration for gizmo handles has to be redone from a fresh screenshot for *each* mode (translate/rotate/scale each render completely different gizmo geometry at the same screen location) — reusing coordinates across modes was a repeated source of wasted cycles during this milestone, worth remembering next time.

**Toolbar primitive insertion**: new `primitives.ts` appends a default statement (`cube([10,10,10]);` etc.) to the end of the document; `App.tsx` tracks a `pendingSelectLast` ref so the render that follows an insertion selects the newly-appended node instead of trying to preserve whatever was selected before. Verified: clicking "Cube" inserted, auto-selected, and rendered a cube with its gizmo correctly placed.

**Real bug found (by Jordan, manually testing the pushed build) and fixed — rotate/scale visually "jumped" past the dragged amount on release.** The pivot group's `rotation={[0,0,0]} scale={[1,1,1]}` props (meant to reset the gizmo's leftover imperative mutation once a fresh render bakes the committed value into new geometry — see the M4-era comment this replaced) never actually did anything: react-three-fiber diffs an element's props against the last value *it* applied, and since that literal value is identical every render, it silently skipped reapplying it — even though `TransformControls` had mutated the live object in between. The result: the *next* render's newly-baked geometry (already reflecting the committed scale/rotation) still had the *previous* drag's leftover value sitting on the same Object3D, so the two multiplied together — e.g. a 3.245x scale drag rendered at roughly 3.245² ≈ 10.5x once its render landed. Confirmed directly (not just inferred) by logging the group's rotation/scale right before the reset call on every geometry change: it read back the exact leftover drag value (`3.245...`) immediately after a scale commit, proving the compounding was real and that the fix's imperative `groupRef.current.scale.set(1,1,1)` (called from a `useLayoutEffect` keyed on the geometry, bypassing prop-diffing entirely) resolves it. Two more things worth remembering from tracking this down: (1) a sphere is the wrong shape to verify rotation with — its symmetry means a *doubled* rotation looks identical to a correct one, which is exactly why this survived this session's own rotate verification earlier; asymmetric shapes (or scale, which visibly stretches) are what actually exercise this class of bug. (2) Position never had this problem in the first place, since `center` is a genuinely different value every render (derived from real geometry), so it was never relying on the same broken "identical-literal-prop" reset path — only rotation/scale, which reset to the *same* constant, were affected.

**Three more real bugs found (by Jordan, testing the doubling-fix build) and fixed — wrong rotate/scale pivot, wrong insertion frame, and garbage multi-axis rotation values.** All three showed up together on a plain `translate([0,0,10]) cylinder(h=20,r=5)`: rotating it visibly displaced the shape (unlike a sphere, which never showed this — its symmetry masks the bug), and after a few rotate/scale drags the source accumulated nonsensical values like `rotate([371.515, 599.278, -793.362])`.

1. *Wrong pivot*: the gizmo was pivoting rotate/scale around the rendered mesh's bounding-box center, but OpenSCAD actually rotates/scales around the shape's own local coordinate origin — for a sphere those coincide, but a default (non-`center=true`) cylinder's bbox center sits at half its height, nowhere near its actual origin at its base. Fixed with `getPivotOrigin` (an enclosing translate's `[x,y,z]`, or the world origin) replacing the bounding-box-center calculation as the pivot group's position.
2. *Wrong insertion frame*: a *new* wrap (e.g. dragging scale for the first time when a rotate already exists) was inserting innermost, right next to the base primitive — i.e. *inside* the existing rotate. Since the gizmo's pivot group itself is never actually rotated between commits (rotation is always baked into geometry, not the transform), every live drag happens in the plain translate-only frame — so a new wrap has to insert *outside* any existing rotate/scale to land in the same frame it was dragged in. This is exactly what the user described as "resizes right while dragging, wrong once re-rendered." Fixed by changing `localInsertPoint` to return the *outermost* position in the local chain instead of the innermost.
3. *Garbage rotation values*: three.js's `Object3D.rotation` uses Euler order `'XYZ'` by default; naively adding those raw components across sequential drags (`x1+x2, y1+y2, z1+z2`) is only valid when every drag stays on the same single axis — combining rotations around *different* axes that way doesn't represent real 3D rotation composition and drifts into nonsense after a few drags. Verified empirically (comparing rendered STL vertices, not guessing) that OpenSCAD's `rotate([x,y,z])` is equivalent to `Rz·Ry·Rx` applied to points — i.e. three.js's Euler order `'ZYX'`, not the default. Fixed `patchRotate` to compose properly: read the live drag as a quaternion delta, convert any existing `rotate([...])` to a quaternion via `Euler(..., 'ZYX')`, compose `delta.multiply(existing)`, and decompose the result back to `'ZYX'` Euler for the new value. Verified two ways: (a) sequential single-axis drags (X then Y then Z) reproduce the exact same combined `rotate([x,y,z])` a single equivalent OpenSCAD call would use; (b) an out-of-canonical-order sequence (Z-axis drag, then a separate X-axis drag) produces a *different*, correctly-decomposed triple that — confirmed by rendering both and diffing STL vertices — is geometrically identical to the reference `rotate([30,0,0]) rotate([0,0,60]) shape()`, i.e. the world-space delta genuinely composes outside whatever existed before, regardless of drag order.

**Architecture change (2026-09-09) — placement is now a real three.js transform, not baked geometry.** Jordan reported one more real issue after the fixes above: "after it rotates it recalculates the scale... looks like scale is applied with global directions in mind." Correct diagnosis — the pivot group's own transform was *never* actually rotated (rotation lived only in the baked mesh vertices), so the scale gizmo's handles always displayed and operated in world axes regardless of how the shape visually looked, and dragging "world Z" on an already-rotated shape stretched along the *original* world Z, not the shape's current tilted Z.

The only clean fix was structural: stop baking translate/rotate/scale into the rendered geometry at all. `openscad-wasm` now renders *just the bare primitive* (`decomposeNode` in `targetedPatch.ts` strips the wrap chain before sending source to WASM); placement is applied as a real three.js transform on the pivot group — `position` = translate, `quaternion` = rotate (via the same verified `'ZYX'` Euler order), `scale` = scale — composed by three.js's own native T·R·S order, which is the same order OpenSCAD itself composes `translate(rotate(scale(primitive)))` in.

This one change resolves the reported bug (the gizmo can now legitimately run in `space="local"` for rotate/scale, since the object genuinely carries its own current orientation) and, as a side effect, deletes most of the complexity the last two rounds of fixes added:
- No more bounding-box-center or `getPivotOrigin` math — the primitive's own geometry already sits at wherever OpenSCAD's local origin is, since nothing is baked into it anymore.
- No more "insert outside vs. inside an existing wrap" puzzle — translate/rotate/scale are three independent slots per node now (not an arbitrary-order chain to search and reason about), always written back in canonical `translate → rotate → scale → primitive` order.
- No more delta/ratio/quaternion-composition math in the gizmo commit handler — the pivot group's position/quaternion/scale *are* the node's absolute transform at all times (nothing is reset to identity or 1 between drags), so a commit just reads the group's current state directly and writes it. The quaternion↔Euler-`'ZYX'` conversion helpers from the previous fix (`transformToQuaternion`/`quaternionToRotateDeg`) are the only pieces of that machinery still needed, now used for direct reads rather than delta composition.
- No more `useLayoutEffect` reset-via-ref hack — `position`/`quaternion`/`scale` are always driven by a freshly-parsed value each render (the same reason `position` never had the M5-launch doubling bug), so ordinary declarative props work correctly again.

**Known, deliberate scope limitation**: `decomposeNode` treats translate/rotate/scale as three independent slots *regardless of the order they're actually written in*, and always rewrites them back in canonical order. A hand-authored file using a non-canonical order (e.g. `rotate(...) translate(...)`, which orbits a shape around the world origin — a real, if unusual, OpenSCAD idiom) will be mis-decomposed and render differently once treated this way. This is a correctness tradeoff scoped to gizmo-editable placement, not a universal OpenSCAD interpreter — consistent with prior scope decisions in this project (M4's vector-only rotate, M5-launch's single-leading-translate skip), and it fails *visibly* (wrong render on load) rather than silently.

Verified: rebuilt the `gizmo-qa.scad` fixture's asymmetric block (`translate(-30,0,0) rotate(0,0,30) cube(...)`) renders pixel-identical to before the refactor; scaling it now visibly stretches along its own tilted axis (confirmed via the scale gizmo's handles themselves appearing rotated to match, not world-aligned); re-scaling an already-scaled shape still composes multiplicatively into one line; rotating the pivot-bug cylinder through a large multi-axis drag still keeps it anchored at its translate point, not just for small single-axis rotations.

**Follow-up, same day: added a local/world toggle for rotate.** Jordan asked whether local vs. global was meant to be user-selectable rather than hardcoded. Added one — but *only* for rotate, not scale: translate stays world-only (moving "up" should mean world-up regardless of a shape's rotation, standard 3D-tool convention) and scale stays local-only (OpenSCAD's `scale()` is always a plain per-axis stretch in whatever frame it's placed in; expressing a world-axis stretch on an already-rotated shape needs a shear-capable `multmatrix()`, which isn't supported, so a "global scale" toggle could only ever be honest for unrotated shapes). Rotate is the one mode where both are meaningful *and* round-trip cleanly with no extra work: the commit handler already reads the pivot group's absolute final quaternion regardless of which space the drag happened in (`space` only changes how a drag *feels* — which axes the rings track — not how the result gets extracted), so the toggle was a two-line change (a `space` prop flip plus a UI button) rather than a new code path. Verified both directions: Local shows gizmo rings tilted to match a rotated shape's current orientation (default); World snaps them to plain world axes even on that same rotated shape; a real drag+commit in World mode produced a single correctly-updated `rotate([...])`, no duplication, pivot still correctly anchored.

**Known limitation, intentionally deferred**: parameter panels (editable fields for a selected node's own arguments, e.g. sphere's `r`) are not built — PLAN.md's M5 description bundles them in, but they're a distinct, self-contained UI piece that didn't fit this pass alongside the gizmo-correctness work above.

**Follow-up (2026-09-11): mirror + color, closing out the rest of M5's transform set.** Both are toolbar toggles/pickers, not gizmo drags — there's no continuous drag gesture that reads as "mirror this" or "recolor this" the way translate/rotate/scale have one.

*Mirror* is implemented as a sign flip on `NodeTransform.scale`, not a new field: an axis-aligned `mirror([1,0,0])` and `scale([-1,1,1])` are the exact same diagonal matrix for a plane through the local origin (the only kind of mirror a toolbar toggle needs), and per-axis diagonal matrices commute, so folding mirror into scale's sign doesn't affect composition order or interact badly with rotate. Three toolbar buttons (Mirror X/Y/Z) each flip one axis's sign on the selected node's current transform and commit through the same `handleTransformCommit` pipeline a gizmo drag uses. `decomposeNode`'s chain-walk now also recognizes `mirror(...)` calls (folding them into a sign accumulator) and `color(...)` calls; `formatTransformPrefix` writes negative scale components back out as real `mirror([1,0,0])`/`[0,1,0]`/`[0,0,1])` calls plus a positive-only `scale(...)` — so the source always reads as an intentional mirror, never as a confusing `scale([-1,...])`. Canonical write-back order is now `color → translate → rotate → mirror → scale → primitive`. Non-axis-aligned hand-written `mirror([1,1,0])` calls are out of scope and degrade gracefully (chain-walk just stops there, same as any other unrecognized wrap, so that node falls back to being treated as one opaque WASM-rendered primitive at identity transform — consistent with the project's existing graceful-degradation policy, not a crash).

*Color* is a `color([r,g,b])` wrap decomposed the same way, stored as `NodeTransform.color: [number,number,number] | null` (`null` is "no wrap," distinct from an explicit black `[0,0,0]`) and applied purely as the mesh's material color in `Viewport.tsx` — it never touches geometry or the WASM render, so there was no need to change the isolated-render pipeline. A plain `<input type="color">` (RGB-only, matching OpenSCAD's `color()` float-triple convention exactly — no conversion math beyond `/255`) plus a "Clear" button drive it. Gizmo drags (translate/rotate/scale) now explicitly carry the node's existing color forward in `Viewport.tsx`'s commit handler, since a drag's absolute-transform commit would otherwise silently drop it.

**Real bug found and fixed during verification, not from first-principles reasoning**: negative-scale (mirrored) geometry risks a winding-order/backface-culling artifact — flipping one axis of a mesh inverts its triangle winding, which can make Three.js treat originally-front-facing triangles as back-facing and cull them, rendering the mesh as hollow/inside-out from most angles. Fixed defensively with `material.side = THREE.DoubleSide` on the shape material rather than trusting Three.js's automatic negative-determinant winding correction to cover every camera angle. Verified concretely under Xvfb (not just reasoned about): mirrored the asymmetric `bracket` primitive (corner-anchored, not centered — a symmetric shape like the default sphere/cylinder can't reveal a mirror at all, the same "don't verify geometry bugs with a symmetric shape" lesson from the M5-launch pivot bugs) via `SCADSTUDIO_EXEC_JS` clicking the real "Mirror X" button, confirmed the source gained a real `mirror([1, 0, 0])` line and the bracket visibly flipped from occupying `x ∈ [0,30]` to `x ∈ [-30,0]` across the grid with normal, solid (non-inside-out) shading; mirrored it a second time and confirmed the `mirror(...)` line disappeared entirely and the bracket returned to its original position (clean round-trip, no leftover residue); separately set the sphere's color via the real color input (dispatching a native `input` event, the trick needed to drive a React-controlled `<input>` from outside React) and confirmed both a real `color([1, 0.133, 0.133])` line appeared and the sphere rendered red, then clicked "Clear" and confirmed the wrap disappeared and the node returned to unselected-default blue.

M5 is now fully done: translate/rotate/scale/mirror/color gizmos/toggles and toolbar primitive insertion are all in place. Only the parameter-panel piece (noted above) remains out of M5's original PLAN.md description, tracked separately since it's UI work, not transform-pipeline work.

**Follow-up (2026-09-11): parameter panel, closing out M5 entirely.** A new toolbar row appears whenever the selected node's own call has arguments (built-in or custom module, doesn't matter): one labeled text input per argument, prefilled with its exact source text.

Deliberately generic rather than schema-driven: `primitiveArgs` reads a call's arguments purely from the grammar's own `argument`/`argument_list` shape (name if the argument is named, else labeled by position `#1`/`#2`/...) — there's no hardcoded table of "`cube` takes `size`/`center`" anywhere. This means positional arguments on a call like `bracket(30, 15, 4)` show as `#1`/`#2`/`#3` rather than `w`/`h`/`thickness`, since resolving that requires reading the module's own definition — that's real, but it's M8's module-introspection scope (which already has to do exactly this to build the custom-module toolbar), not a new thing to build here. Each field edits as opaque text (whatever the user types replaces the argument's value byte range verbatim via a new `patchArgument`, same minimal-diff philosophy as `patchTransform`) rather than a typed/validated numeric input — so `r=8` can be edited to `r=8+2` or any other valid expression, not just a literal number, at the cost of no client-side validation (invalid text becomes a parse error, handled by the same graceful degradation as any other bad edit).

`decomposeNode`'s `DecomposedNode` gained a `primitiveNode` field (the actual base-call AST node, not just its byte offset) so `primitiveArgs` doesn't need to re-walk the wrap chain a second time.

Implementation note on the input fields themselves: they're uncontrolled (`defaultValue`, not `value`), keyed on `${index}-${name}-${valueText}` — committing a change causes a re-render that produces a new `valueText`, which changes the key and forces React to remount the input with the freshly re-parsed (possibly reformatted) text, rather than fighting React's controlled-input value on every keystroke. Commits fire on blur or Enter, not on every keystroke (would otherwise re-render/re-derive on every character).

**Verified with the real running app, not just code review**: `SCADSTUDIO_EXEC_JS` selected the sphere (`sphere(r=8)`), confirmed the panel showed exactly one field (`r: 8`), programmatically set it to `20` and dispatched a real blur, and confirmed both the source became `sphere(r=20);` and the viewport rendered a visibly larger sphere (camera auto-fit adjusted too). One real test-script gotcha hit along the way (not a product bug): calling `.blur()` on an element that was never actually focused is a no-op in Chromium — no blur event fires — fixed by calling `.focus()` first. Also verified the cylinder (`cylinder(h=20, r=5, $fn=32)`) showed all three fields correctly labeled, including the `$fn` special variable, confirming the generic argument reader isn't limited to plain identifiers.

M5 (full transform set + toolbar primitive insertion + parameter panels) is now 100% done, matching its original PLAN.md scope exactly. M6 (booleans) is next.

## M6 build notes (2026-09-11) — multi-select + boolean wrap-in-block

First slice of M6: shift-click multi-select in the viewport, and a Union/Difference/Intersection toolbar that wraps the selected nodes' verbatim source into a new boolean block. Explicitly **not** attempted in this pass (see "Known limitations" below): modifier characters (`# % ! *`) and per-child selection/dragging *inside* a boolean group once merged — both real M6 scope, deliberately deferred.

**Multi-select**: `selectedIndex: number | null` became `selectedIndices: number[]`, ordered by *selection sequence* (shift-click order), not document order — this matters because `difference()`'s first child is the base and the rest are subtracted, so which shape the user clicked *first* is semantically load-bearing, same as any real CAD tool's boolean tool. The last entry is the "primary" selection: the one thing every single-target feature (gizmo, mirror, color, parameter panel) still operates on, so none of that M4/M5 code needed to change its own logic, only swap `selectedIndex` for a derived `primarySelectedIndex`. Shift-clicking an already-selected node toggles it back off (standard multi-select convention). Text-based selection (clicking in Monaco) stays single-select only — deliberately out of scope, since Monaco's cursor is inherently a single position, not a natural fit for expressing "add to selection."

**`wrapInBoolean`**: a new minimal-diff codegen function (not a whole-file regen) — single left-to-right pass over the selected nodes in *document* order: the earliest one's byte range is replaced with the new `union()`/`difference()`/`intersection() { ... }` block (body ordered by *click* order, not document order — see above), every other selected node's byte range is deleted entirely (plus one trailing newline, so removing a shape doesn't leave a blank line behind). The merged statement always lands at the exact array index of whichever selected node had the smallest index — nothing before it ever moves — so selecting the merged node after the edit reuses the same `pendingSelectAfterEdit` mechanism as `pendingSelectLast` (primitive insertion), just targeting a computed index instead of always the last node.

**Real bug found and fixed — positional arguments were silently invisible to the M5 parameter panel.** Testing M6 with `cube([20,20,20], center=true)` (needed as an actually-overlapping-shapes fixture, see below) surfaced that the parameter panel showed only `center: true`, silently dropping the `[20,20,20]` size vector. Root cause: the grammar's `argument` rule only tags a `value` field on the *named* branch (`name '=' value`) — a bare positional argument is just `$._value` with no field name at all (confirmed by reading `grammar.js` directly), so `argument.childForFieldName('value')` returns null for any positional argument, and `primitiveArgs` was silently `continue`-ing past it. This is the exact same gotcha `readVectorCall` (M4/M5) already had to handle by reading `.child(0)` instead of a field name — `primitiveArgs` just hadn't been written against that lesson yet. Fixed with `argument.childForFieldName('value') ?? argument.child(0)`. This is a real, user-visible bug that shipped in the M5 parameter panel commit and would have affected any built-in call with a leading positional argument (`cube`, `cylinder`'s implicit forms, custom modules called positionally, etc.) — not something the M5 sphere/cylinder verification runs happened to exercise, since both of those examples used all-named arguments.

**Verified with the real running app, including a real CSG cut, not just a non-overlapping coincidence.** The default demo scene's shapes don't spatially overlap, so an early test (`difference()` between the demo's cylinder and sphere) round-tripped the source correctly but rendered as a visually unchanged cylinder — mathematically correct (subtracting a non-overlapping shape is a no-op) but not proof the CSG pipeline actually cuts anything. **Follow-up (2026-09-15): three fixes from real beta.3 testing feedback.** Jordan tested `v0.1.0-beta.3` (the first release with M6 multi-select) and reported: position was missing from the M5 parameter panel, it wasn't clear which shape a difference() subtracts *from* vs. which it subtracts, and the camera kept re-centering on every edit instead of staying where the user left it.

2. **Base vs. tool(s) coloring.** `NodeModel` (Viewport.tsx) took a plain `selected: boolean` before; now takes a `SelectionRole` (`'none' | 'base' | 'operand'`) computed from position in `selectedIndices` — index 0 (the click-order "base", same shape difference() subtracts from) keeps the existing amber `SELECTED_MESH_COLOR`, every other selected shape gets a new red `OPERAND_MESH_COLOR`. 3. **Camera stops auto-recentering on edits.** `<Bounds fit clip observe>` re-fits the camera on every children change by design — that's what was yanking the camera back to center on every gizmo drag or parameter edit, not just on load. First attempt: drop `observe`, remount `<Bounds key={fitToken}>` only when App.tsx's `fitToken` (`` `${filePath}:${resetViewToken}` ``) changes — i.e. only on file-open or an explicit new "Reset View" button. After orbiting away from the initial view, every subsequent "reset" was just re-framing along the already-orbited direction. Fixed with a `FitController` child component (lives inside `<Bounds>` to access `useBounds()`) that, on `fitToken` change, first snaps `camera.position` back to the same canonical `DEFAULT_CAMERA_POSITION` the `<Canvas>` itself starts with, *then* calls `bounds.refresh().fit().clip()` — so the direction `reset()` preserves is always the canonical one. `<Bounds>` no longer needs `fit`/`clip`/`observe`/`key` at all; `FitController` is now the single trigger point for every fit, including the original load-time one.

**Real bug found and fixed while verifying `%`**: `decomposeNode`'s `primitiveStart` incorrectly included a leading modifier character whenever a node had a modifier but no translate/rotate/scale wrap to walk through (e.g. bare `%cube(10);`) — the wrap-walk loop only ever advances `current` past `top` when it recognizes a wrap keyword, so with zero wraps, `current` stays equal to `top`, whose `startIndex` is the modifier's own position, not the primitive's. `primitiveSource` then sent the literal modifier character to `openscad-wasm` as part of the "bare primitive" source — which OpenSCAD then correctly (per real semantics) rendered as empty/excluded geometry for `%`, silently producing a 0-triangle STL that got skipped ("Rendered 2/3 nodes", read like a real failure). `#` happened to look fine in initial testing since OpenSCAD's `#` doesn't exclude from output, which is exactly why this needs a systematic fixture pass across all four rather than trusting one working case. Fixed by computing `wrapStart` to skip past a detected leading modifier node, and `primitiveStart` as `Math.max(current.startIndex, wrapStart)` — correct whether or not the loop ever advances, since an advanced `current` is already past both the modifier and any consumed wraps regardless.

## M7.5 build notes (2026-09-17) — slice 1: global plane picker + camera lock

Before starting M7.5 for real, surveyed OpenSCAD's native 2D toolkit and settled the sketch-constraints question (both folded into the "Sketch mode (M7.5)" section above rather than repeated here: no native arc/fillet primitive, so drawn arcs/rounds are always a point-dense `polygon()` approximation regardless of tooling; `offset()`/`projection()` are real native ops worth their own toolbar buttons; constraints are tiered — cheap draw-time snapping ships as part of M7.5 itself, real parametric point-drag constraints route through M12's existing solver-based-constraints work instead of a second, sketch-only solver).

Given the size of the full milestone (four new subsystems per the write-up above), deliberately scoped a first slice rather than attempting all of it: **a plane picker (global XY/XZ/YZ only, no face-picking yet) plus a camera mode that animates to look straight at the chosen plane and locks rotation** — no drawing, no sketch-entity model, no extrude hand-off yet. This proves out the single riskiest, most novel piece (a real camera-mode switch, something the app has never needed before) in isolation, same spirit as M4 shipping translate-only before M5 added the rest of the gizmo set.

**Reused `Bounds.moveTo()/.lookAt()` instead of writing a second animation system.** `FitController` (M6-era) already established the pattern of a component living inside `<Bounds>` that reacts to a prop change via `useBounds()`; `SketchController` (Viewport.tsx) follows the identical shape, but calls the lower-level `moveTo(position).lookAt({ target, up })` directly instead of `fit()/reset()`, since a sketch-plane view is a **fixed given orientation**, not something derived from current content/camera state the way "fit to scene" or "reset to default" are. This is deliberately the same "animate camera to a target orientation" primitive PLAN.md's M7.5 point 5 already flagged the nav-cube would need — building it correctly now means the nav-cube can reuse it later instead of getting its own animation path.

**Axis convention, explicitly checked before picking plane vectors**: this app has never remapped OpenSCAD's `[x,y,z]` onto three.js's Y-up convention anywhere (`position={mesh.transform.translate}` uses the tuple directly, confirmed by grep) — so "XY plane" for sketch purposes had to mean "the plane where the raw third tuple component is 0," matching real OpenSCAD's own XY/XZ/YZ naming, not three.js's default framing. (**Correction, 2026-10-15**: the coordinates were never remapped, but the *camera* was still three.js's default Y-up, so the free-orbit view showed OpenSCAD's +Y as vertical — see the nav-cube build notes below, which switched the viewport to Z-up.) Picked camera position/up tuples accordingly (`XY: position [0,0,60], up [0,1,0]`; `XZ: position [0,-60,0], up [0,0,1]`; `YZ: position [60,0,0], up [0,0,1]`) and used them directly as three.js vectors, consistent with how translate/rotate already work everywhere else — no new remap introduced.

**Rotation lock**: a `useEffect` in the main `Viewport` component toggles `orbitControlsRef.current.enableRotate` based on whether `sketchPlane` is set (pan/zoom stay enabled). "Exit Sketch" clears `sketchPlane` **and** bumps the existing `resetViewToken` in the same handler, reusing `FitController`'s fit-to-content behavior (the same thing "Reset View" already triggers) instead of needing to remember/restore whatever the camera's pre-sketch state was.

**Verified with the real running app**, all three planes, against the default multi-shape demo scene: XY produced a true top-down orthogonal view (spheres rendered as perfect circles, confirming no foreshortening); XZ and YZ produced the other two mutually-orthogonal views (cylinder showing its side profile from XZ/YZ instead of the circular end-on view XY would give it); "Exit Sketch" returned to the exact original isometric framing. Also explicitly tried to orbit-drag while in sketch mode (the same drag gesture that rotates the camera outside sketch mode) and confirmed the view was pixel-identical before and after — rotation lock holds.

**Known limitation, intentionally deferred**: plane-view camera distance is a fixed constant (60 units), not content-fit the way the default/reset view is via `Bounds.fit()` — fine for the default demo scene's scale, will look wrong (too close/too far) for very small or very large models. Worth switching to a fit-based distance once sketch mode has real content to frame (i.e., once drawing exists — slice 2+), rather than guessing now.

**Real bug found and fixed, same day**: entering sketch mode on an empty scene (no geometry yet — a genuinely common real case, arguably *the* common case for starting a new sketch-first model) silently did nothing — the toolbar correctly flipped to "Sketching on XY plane," but the camera never moved. Root cause: `<Bounds>` (and everything inside it, including `FitController` and the new `SketchController`) was only ever rendered when `visibleMeshes.length > 0`, so on an empty scene neither controller ever mounted. This turned out to be a **pre-existing bug, not one this slice introduced** — "Reset View" on an empty scene has been silently broken the same way since M6. Fixed by rendering `<Bounds>`/`<Center>` unconditionally; `Bounds.refresh()` already falls back gracefully on an empty bounding box (confirmed by reading its source, same read that found the M6-era `reset()`/`fit()` direction bug), and `<Center>` with zero children is a no-op, so there was no real reason for the gate to exist. Verified: sketch-plane entry now correctly locks the camera on a genuinely empty file; re-verified the default demo scene's normal load/fit still matches the prior baseline exactly (no regression from removing the gate).

## M7.5 build notes (2026-09-19) — slice 2: click-to-place point drawing → real polygon()

Second slice: interactive point placement while sketching, closing into a real `polygon()` statement on "Finish Sketch." Scoped narrowly again — plain click-to-add-point only, no rubber-band cursor preview, no click-near-first-point-to-close, no snapping (that's its own tier, per the constraints write-up above) — same "prove the mechanism, defer polish" pattern as slice 1.

**Point placement uses a real invisible mesh + r3f's own click system, not raw DOM events or manual raycaster math.** `SketchDrawingPlane` (Viewport.tsx) is a large (1000×1000) plane mesh rotated to match the active sketch plane, with `meshBasicMaterial visible={false}` — invisible but still raycastable, since three.js's raycasting checks `Object3D.visible` (left at its default `true`), not `material.visible`. Its `onClick` reads `event.point` (r3f's world-space hit position) and inverse-rotates it back through the plane's own rotation to recover the sketch-local `(u, v)` the click landed on. Chose this over computing the ray-plane intersection by hand (`Raycaster.ray.intersectPlane`) specifically so it stays inside r3f's normal event system rather than fighting it with a second, parallel one.

**Existing shapes had to stop intercepting clicks while sketching, or the drawing plane would only ever receive clicks where nothing else was in front of it.** r3f's raycasting hits whichever object is *closest* along the ray — if an existing shape sat between the camera and the sketch plane at a given screen point, that shape would swallow the click before it ever reached the plane. Fixed with `NodeModel`'s new `sketchActive` prop, passed through to `<mesh raycast={sketchActive ? () => null : undefined}>` — overriding three.js's raycast callback to a no-op disables hit-testing for that mesh entirely while sketching, guaranteeing every click reaches the drawing plane regardless of what's visually in front of it from the camera's angle. Verified directly: clicked squarely on top of the default demo scene's sphere and cylinder while sketching and confirmed points were added at the plane intersection, with no selection change and no interference.

**Rotation consistency between the live preview and the committed source is structural, not just "tested and it happened to match."** `SKETCH_PLANE_ROTATIONS` (Viewport.tsx, exported) is the one source of truth for the `rotate([...])` that places a flat sketch onto each plane — `SketchPointsPreview` applies it (via the existing `transformToQuaternion`) to render each point's live world position, and `appendSketchPolygon` (primitives.ts) takes the identical tuple as a parameter to emit the final `rotate([...]) polygon(...)` statement. There's no second place either value could be defined, so preview and commit can't drift apart independently — a change to one plane's rotation automatically keeps both in sync. Identity rotation (the XY plane) omits the `rotate()` wrap entirely, matching how `patchTransform` already skips identity transform components elsewhere.

**The committed polygon needed no new integration work to become a real, selectable, editable node** — `rotate([90, 0, 0]) polygon(points=[...]);` is just an ordinary top-level statement, so `sceneGraph.ts`/`decomposeNode`/`primitiveArgs` handle it via the exact same generic machinery as every other node (same finding as M7's extrude tools). It picks up the M7 bare-2D-render fix automatically too, since `polygon()` alone is exactly the kind of pure-2D geometry that fix exists for.

## M7.5 build notes (2026-09-20) — extrude-the-selection, and a systemic double-render bug

Two issues surfaced testing slice 2's actual point: drawing a sketch is only useful if you can then extrude *it*.

**Real gap found: "Linear Extrude"/"Rotate Extrude" never extruded the selected sketch — they always inserted an unrelated fresh default shape.** Both buttons were still wired to `handleInsertPrimitive` (the plain M5 Insert-toolbar path: always append `PRIMITIVE_DEFAULTS[kind]`, ignore selection entirely), so clicking "Linear Extrude" after finishing a sketch just appended a brand-new `linear_extrude(height=10) circle(r=5, $fn=32);`, unrelated to anything just drawn — the exact confusion Jordan hit ("that made a cylinder?"). Fixed with `wrapInExtrude` (targetedPatch.ts), the single-node analog of `wrapInBoolean`: replaces the *selected* node's own byte range with `linear_extrude(height=10) { <verbatim node source> }` (or `rotate_extrude($fn=48) { ... }`), in place — same minimal-diff philosophy as every other targeted patch here. `handleExtrude` (App.tsx) wraps the primary selection when one exists, falling back to the old insert-a-default behavior only when nothing is selected, so the buttons still work as a plain toolbar insert on an empty selection. Toolbar label now reads "Extrude (selected):" whenever something's selected, so which behavior a click will trigger is visible before clicking, not just discoverable after the fact.

**Real bug found and fixed: every programmatic edit in the app has been double-rendering since M2/M4, not just sketch finish.** Investigating a second report ("rendered 3 of 4 nodes" on a drawn polygon) that didn't reproduce with the same polygon in isolation led to instrumenting `runRender` directly, which showed it firing *twice* per single toolbar action, from two different call sites: once immediately (every edit handler's own direct `runRender(next)` call), and once again ~400ms later via `handleSourceChange`'s debounce path. Root cause: `Editor.tsx`'s `onDidChangeModelContent` handler calls `onChange` unconditionally — including when the content change came from *this app's own* `model.setValue(value)` a few lines below (used to push every programmatic edit into Monaco), which is indistinguishable from real typing to that handler. So every gizmo commit, toolbar insert, boolean wrap, modifier toggle, argument edit, and now sketch finish/extrude has been triggering a full second render pass of identical content ~400ms after the first, this whole time. This is the content-change sibling of a bug already found and fixed in M5 (Monaco's cursor reset on `setValue()` masquerading as a user click) — that fix only guarded the cursor-position side effect, not the content-change side effect, so half of the same underlying problem shipped anyway. Fixed identically: `onDidChangeModelContent`'s event carries `isFlush` (Monaco's own flag for "this change came from `setValue()`"), the exact content-change analog of the cursor event's `ContentFlush` reason already guarded against — skip the `onChange` call when `e.isFlush` is true.

**Why this plausibly explains the "3 of 4 nodes" report, even though it didn't reproduce with an isolated fixture**: a redundant second render of *identical* content should be deterministic and harmless on its own, but two back-to-back WASM/Manifold invocations racing (the coalescing runner's own "only the latest survives" logic means the second pass's result unconditionally overwrites the first's, whichever finishes last) is exactly the kind of situation where any non-determinism in near-degenerate geometry (borderline self-intersecting polygons, e.g. from two sketch points landing very close together) could make one of the two redundant passes fail when the other wouldn't have. Fixing the double-render doesn't guarantee every possible degenerate-polygon case renders cleanly, but it removes a real, systemic source of wasted/racing compute that had gone unnoticed for months of milestones — worth having found regardless of whether it's the *complete* explanation for that specific report.

**Fixing this broke the SCADSTUDIO_TEST_EDIT test harness, which had to be fixed too.** `SCADSTUDIO_TEST_EDIT` (main/index.ts) injected content via `window.__testEditor.setValue(...)` — the *raw* Monaco instance, bypassing React state entirely — relying on the exact same `onDidChangeModelContent` → `onChange` round-trip to carry that content back into `App.tsx`'s `source` state, since nothing else did. Guarding that event against `isFlush` silently broke the harness the same way (both call sites set `isFlush: true`; the event carries no way to distinguish "test harness bypass" from "the programmatic edit this guard exists to skip"), which briefly produced a confusing false lead — a debug session that appeared to reproduce "3 of 4 nodes" was actually running against the untouched default demo scene, not the intended test fixture, because the injected content silently never reached React state. Fixed with a dedicated test-only path instead of relying on Monaco's event system at all: `window.__testSetSource` (App.tsx) calls `setSource`/`runRender` directly, and `main/index.ts` now calls that instead of `__testEditor.setValue(...)`. The raw `__testEditor` handle stays exposed for ad-hoc manual devtools debugging, just no longer load-bearing for the automated harness.

**Verified with the real running app**: drew a 4-point sketch, "Finish Sketch" (1 expected error — bare polygon's normal fallback retry, not 2), selected result showed "Extrude (selected):" in the toolbar, clicked "Linear Extrude" and got `linear_extrude(height=10) { polygon(points=[...]); }` — a genuine extruded 3D solid with real depth, zero additional render errors (a real 3D shape never needs the 2D fallback). Re-confirmed the test harness now correctly loads intended fixture content again (the false-lead debug screenshot's default-demo-scene content was the tell that something was off).

## M7.5 build notes (2026-09-22) — slice 3: face-based plane picking, and two more render bugs

Third slice: the other half of the original ask ("pick a plane, whether it's global or a face") — "Pick Face" lets a click on any existing solid's flat face derive a sketch plane from that face's origin/normal, generalizing slice 1's three hardcoded global planes into an arbitrary-origin, arbitrary-orientation `ActiveSketchPlane`.

**Generalized the plane data model from a `'XY'|'XZ'|'YZ'` enum to `{ kind, origin, rotationDeg }`.** Global planes always passed through the world origin with one of three fixed rotations, so slice 1/2 never needed to carry an explicit origin. A face-picked plane sits wherever the face is, so `ActiveSketchPlane` (Viewport.tsx) now always carries both; `buildGlobalSketchPlane('XY'|'XZ'|'YZ')` builds the old three cases from the same hand-picked rotation table (regression-verified identical output), and `SketchController`'s camera-lock math for `kind === 'face'` derives the camera position from `origin + distance * (rotation applied to +Z)` instead of a lookup table, since there's no finite set of face orientations to hand-pick. `appendSketchPolygon` (primitives.ts) gained the same `origin` parameter, emitting `translate(origin) rotate(rotationDeg) polygon(...)` — identity components still omitted, so a global-plane sketch (origin always `[0,0,0]`) emits exactly the same bare `rotate()`-or-nothing wrap as before this generalization.

**Face picking reuses r3f's own click/raycast system, not manual geometry math.** `NodeModel` gained a `pickingFace` prop; while true, its `onClick` reads the click event's own `face.normal` (already computed by three.js's raycaster) and `point` (world-space hit position), converts the normal to a quaternion via `setFromUnitVectors(+Z, worldNormal)`, and reports `(point, quaternionToRotateDeg(rotation))` as the new plane — the exact same "let r3f's event system do the geometry" choice slice 2 made for click-to-place points. Unlike sketching itself, face-picking does *not* disable other shapes' raycasting (`pickingFace` isn't wired into the `sketchActive` raycast-disable) — the user needs to freely click *any* face across the whole scene, and the rotate-lock `useEffect` was scoped to key on `activeSketchPlane` only, so the camera also stays free-orbit during picking (needed to see/reach a face pointing away from the current view).

**Real bug found: `wrapAsThinExtrude`'s 2D-fallback wrapper nested file context (module/function definitions) inside the synthetic extrude block.** `primitiveSource()` (targetedPatch.ts, now deleted) returned context and primitive already concatenated as one string; `wrapAsThinExtrude` wrapped that *entire* string in `linear_extrude(height=0.01) { ... }`, so a file with a preceding `module bracket(...) { ... }` produced `linear_extrude(height=0.01) { module bracket(...) {...} ... }` — a module definition somewhere it was never written to be, inside a block it has no business being nested in. Every bare-2D node in any file that also defines a module or function (i.e. any file using the demo fixture, or any real-world parametric file) failed **both** the normal render attempt and this fallback retry, going from "expected, silent" (M7's whole reason for the fallback existing) to a genuine render failure — this is very likely the real explanation for Jordan's original "rendered 3 of 4 nodes" report on a plain 3-point triangle, a shape structurally incapable of the self-intersection theory floated at the time. Fixed by splitting `primitiveOnlySlice` (primitive only, no context) out from the deleted `primitiveSource`, and changing `wrapAsThinExtrude(context, primitive)` to take context and primitive as separate parameters, concatenating context *outside* the synthetic block instead of inside it.

**Second, unrelated real bug found: `wrapInExtrude` also nested a plane's `rotate()` on the wrong side of the extrude.** Once the above was fixed, extruding a face-picked (or XZ/YZ-plane) sketch still failed — this time as a *genuinely 3D* `linear_extrude(height=10) { translate(...) rotate(...) polygon(...); }` node, failing both the normal attempt and the (already-unnecessary) 2D fallback. Root cause needed OpenSCAD's own stderr to find (main/index.ts's `printErr` is normally a no-op; temporarily logging it surfaced `WARNING: Scaling a 2D object with 0 - removing object` / `Current top level object is empty.`): `linear_extrude` only accepts a child that's genuine 2D geometry lying flat in the XY plane, and `wrapInExtrude` (the "Linear Extrude" button's codegen) wrapped the *entire selected node's source* — including its own `translate()/rotate()` wrap — inside the new extrude block, so the rotate ended up applied to the 2D polygon *before* extrusion instead of to the finished 3D solid *after*. Any rotation with a nonzero X or Y component tilts the profile out of the XY plane, which OpenSCAD's 2D engine can't represent, so it silently drops the geometry rather than erroring loudly — explaining why this only showed up on the XZ/YZ/face-picked planes (their rotations aren't purely Z-axis) and never on XY (identity rotation, so the bug was a no-op there). Fixed by having `wrapInExtrude` decompose the node the same way `patchTransform` already does, and re-emit the wrap prefix (via the same `formatTransformPrefix` `patchTransform` uses) *ahead of* the extrude block instead of inside it — `translate(...) rotate(...) linear_extrude(height=10) { polygon(...); }`, transform-of-the-solid instead of transform-of-the-profile. This was a latent bug in slice 2's XZ/YZ extrude path too, not something slice 3 introduced — just never previously exercised end-to-end (slice 2's own verification only drew/finished on XZ, per its build notes above, and never clicked Extrude afterward).

**Verified with the real running app, full pipeline, all four plane kinds**: for XY, XZ, YZ, and a face picked off the demo bracket's top face — entered sketch mode, drew a 3-point triangle, "Finish Sketch" (1 expected error, the normal bare-2D fallback retry), selected result showed "Extrude (selected):", clicked "Linear Extrude", got a genuinely extruded 3D wedge with zero additional render errors and correct source (`rotate([0, 90, 0]) linear_extrude(height=10) { polygon(...); }` for YZ; `translate([...]) rotate([-90, 0, 0]) linear_extrude(height=10) { polygon(...); }` for the picked face; bare `linear_extrude(height=10) { polygon(...); }` for XY, no prefix, confirming the fix is a no-op for the already-working identity-rotation case). Screenshots confirm the extruded solid renders in the correct position/orientation relative to the plane it was sketched on in every case.

## M7.5 build notes (2026-10-15) — on-plane editing of an already-placed sketch

Fourth slice: point 3 of the M7.5 write-up ("on-plane drag editing"). Selecting a sketch the app can round-trip shows an **"Edit Sketch"** button in the Sketch toolbar group; it re-enters sketch mode on the plane the sketch was drawn on, loads its committed points as handles, and **"Save Sketch"** writes the edited points back into the same `polygon()` — only the points vector's own bytes change (`patchSketchPoints`, targetedPatch.ts), so the plane wrap, any `linear_extrude` around it, modifiers, color and formatting survive untouched. "Cancel" discards the edit with the source unchanged.

**The plane comes back from the source, not from remembered state.** `readSketchProfile` (targetedPatch.ts) reuses `decomposeNode` to read the sketch's `translate()`/`rotate()` wrap — exactly what `appendSketchPolygon` emitted from the original `ActiveSketchPlane` — and `sketchPlaneFromTransform` (Viewport.tsx) turns that back into a plane: a wrap matching one of the global planes exactly (origin 0, same rotation) maps back to XY/XZ/YZ so it gets the same hand-picked camera framing it was drawn with, anything else (a picked face, or a sketch the gizmo has since moved/rotated) goes through the general face-derived camera path. This means a sketch is editable after a reload or after being moved with the gizmo, and a hand-written `rotate([90,0,0]) polygon(points=[...])` is editable too — the .scad file stays the only source of truth, same constraint as everywhere else in the plan.

**Which nodes qualify, deliberately strict.** A bare `[translate] [rotate] polygon(points=[...])` or the same with a single-child `linear_extrude` between wrap and polygon (what Finish Sketch → Linear Extrude produces — editing the extruded feature's profile is the Onshape "edit the sketch under the extrude" workflow). Not offered (no button) when: any point is an expression rather than a literal number (rewriting `[w, 0]` as `[10, 0]` would silently destroy parametric intent); there's a `scale()`/`mirror()` wrap (handles live in the plane's unscaled frame); the profile is under `rotate_extrude` (its XY profile is revolved into XZ, so on-plane handles wouldn't line up with the solid); fewer than 3 points.

**Editing interactions**: drag a handle to move it; click on the plane to insert a vertex into whichever edge passes nearest the click, including the closing edge (`insertIntoNearestEdge`, new `sketchEditing.ts` — appending at the end, as draw mode does, would always splice into the closing edge wherever you clicked); double-click a handle to delete it (floor of 3 while editing a committed polygon); "Undo" steps back through a per-session snapshot stack (a whole drag is one step — the snapshot is taken on the drag's first movement, so a press without movement records nothing). The edited node renders as a faint translucent "before" reference behind the live closed outline. Dragging also works in plain draw mode before Finish Sketch, since it's the same handles; draw mode's "Undo Point" became the same history-based "Undo".

**Drag mechanics**: the handles start the drag (`onPointerDown`), but the moves come from the existing invisible `SketchDrawingPlane` — the 0.8-unit handle sphere falls out from under a fast cursor immediately, the 1000×1000 plane never does — converted to sketch-local (u, v) through the same inverse-rotation path click-to-place already used. Release is caught on `window` (the cursor can be anywhere by then), and the native `click` that follows a drag's mouseup is suppressed with the same deferred-flag trick as `isTransformingRef`, so ending a drag doesn't also insert a point. Orbit controls are disabled for the drag's duration.

**Real bug found while verifying: r3f silently starved the drag of moves.** The first working drag landed short of the cursor, deterministically (always the 10th of 12 steps). Cause, confirmed in r3f's own `events` source: a handle's `onPointerOver` called `stopPropagation()`, and r3f *remembers* a stopped hover (`hoveredItem.stopped`) and keeps stopping every later `pointermove` for as long as the cursor stays over that object — so the drawing plane behind the handle stopped receiving exactly the moves that drive the drag (the handle follows the cursor, so the cursor is over it for most of a drag). Fixed by not stopping propagation in `onPointerOver`; worth remembering for any future r3f hover/drag combination.

**Second issue found from screenshots, fixed**: on a face-picked plane, neighboring solids often sit between the camera and the sketch (in the test scene, the demo sphere covered one of the triangle's handles). Hit-testing already ignored them (`sketchActive`), but the handle was invisible. The sketch outline and handles now render with `depthTest={false}` and a late `renderOrder`, so the overlay always draws on top — this also benefits plain drawing.

## M7.5 build notes (2026-10-15) — slice 4: draw-time snapping

The cheap, solver-free constraints tier from the "Sketch mode" write-up: snapping while drawing, on all four plane kinds (XY, XZ, YZ, picked face).

**Pure snap logic, separate from the viewport (`sketchSnap.ts`).** `snapSketchPoint(raw, placedPoints, planeGeometry, settings, tolerance)` works entirely in sketch-local (u, v) — the same space clicks are converted to and `appendSketchPolygon` emits — so the snapped number *is* the number that lands in the committed `polygon()`, with no second conversion that could drift from the preview. Priority, highest first: **close the loop** (the first point, once 3+ exist) → **existing on-plane vertices, edge midpoints, the plane origin** → **a point along an existing on-plane edge** → **horizontal/vertical alignment** with points already placed this session (independent per axis, most recent point first, drawn as a dashed guide) → **grid** (0.5/1/2/5/10, default 1) → free. Toolbar: a Grid checkbox + spacing dropdown and a Points/edges checkbox (kept across sessions, since they're working preferences); **Alt-click bypasses snapping**. The 10-screen-pixel snap radius is converted to sketch units from the camera FOV and the hit's depth on every pointer event, so it feels the same at any zoom.

**Existing geometry = on-plane feature edges only.** `extractOnPlaneGeometry` runs three's `EdgesGeometry` (20° threshold) over each visible shape's STL — so box edges and cylinder cap outlines count, but triangulation diagonals and shallow facet seams don't — applies each node's T·R·S transform, converts into plane-local coordinates, and keeps only edges whose two endpoints both lie within 0.005 of the plane. Off-plane geometry is deliberately not projected: a snap target the drawn polygon can't actually touch would be a trap. Cached per STL buffer (`geometryFor` in Viewport.tsx now shares one parsed geometry between rendering and snapping) and recomputed only when the plane, the shapes or the toggle change, not per pointer move.

**Snapping applies to editing too.** Dragging a handle in an edited sketch snaps like drawing does, against the *other* points and existing on-plane geometry (the dragged point itself and the sketch being edited are excluded, so it can't snap to its own pre-edit outline); click-to-insert snaps its new vertex the same way. Closing the loop is drawing-only. The Snap controls show in both modes, and Alt bypasses for a single click or drag.

**Closing the loop.** Clicking the first point (hover shows a larger "Close loop" marker) calls the same handler as "Finish Sketch". Re-clicking the last snapped spot is ignored, since grid snapping makes that easy to do and it would only add a zero-length edge.

**Face-picked planes now use a canonical origin.** Previously the origin was the raw raycast hit point, so a face sketch's (0, 0) was wherever the click landed, grid snapping would have been offset by an arbitrary amount, and the emitted source had a `translate([13.2, 4.7, 4])` that meant nothing. `buildFaceSketchPlane` now uses the world origin's projection onto the face (`normal · (normal · point)`, rounded to 3 decimals), so a face at y=15 emits `translate([0, 15, 0])` and grid points land on round world coordinates. The click still decides where the camera looks (a new `focus` field). Note for anyone reading face-plane coordinates: local v follows the plane's own rotation, so on a `rotate([-90, 0, 0])` face, +v is world −Z.

**A real bug found while verifying, fixed.** *After any sketch session every shape stayed unclickable until restart* — no selection, no Pick Face. `NodeModel` disables raycasting while sketching via `raycast={sketchActive ? () => null : undefined}`, but r3f doesn't restore a mesh's default function prop when it goes back to `undefined`, so the no-op stuck. ## M7.5 build notes (2026-11-22) — richer sketch tools, several loops per sketch, Offset (M7.5 complete)

Last M7.5 slice, the "richer sketch tools and several profiles per sketch" item from the build order. With it M7.5 is done; the rest of the original write-up's wish list is listed under "Deferred" below.

**Tool row.** Sketch mode now shows Line, Arc, Rectangle, Circle and Edit Points, plus a hint saying what the next click does (it changes as a tool collects its clicks). Rectangle takes two opposite corners. Circle takes a center, then a rim point, and the rim point becomes the first vertex, so it lands exactly where it was snapped. Arc is a 3-point arc that continues the open polyline: click the end, then a point it passes through; ending on the polyline's first point closes the loop. Collinear points give a straight edge. Circles and arcs are point runs in the polygon (OpenSCAD has no arc primitive, see the 2D toolkit survey above), with a 16/32/64 segments dropdown; an arc gets the density a full circle with that setting would have. All shape math is in `sketchShapes.ts`, and the live dashed preview and the commit call the same functions, so the preview is exactly what gets written. Points come out rounded to 3 decimals there, the same rounding `formatNumber` applies, so snap targets, preview and source carry identical numbers.

**Several loops, one polygon.** The session state is now `{ profiles, open }` (closed loops plus the polyline being drawn, `sketchEditing.ts`), and handles are addressed as `{ profile, point }`. Clicking the first point closes a loop but no longer finishes the sketch, so more loops can follow. Finish Sketch writes one `polygon(points=[...], paths=[[...], [...]])`. OpenSCAD fills that even-odd, so a loop inside another is a hole, which matches what any CAD sketch does with a circle inside a rectangle. A single loop still writes the plain `polygon(points=[...])` it always did. We picked one polygon with paths over several polygons in a block because it stays one node: it selects, extrudes, offsets and re-opens as one sketch, and holes come free.

**Editing round-trips paths.** `readSketchProfile` reads `paths=` (named, positional, or written before `points=`, and treats `paths=undef` as absent). It rejects non-literal or out-of-range indices and paths with fewer than 3 points, like it already did for points. Save keeps the minimal-diff rule. Only the points vector changes, plus the paths vector when the polygon already has one; a polygon that never had paths and gains a loop gets `, paths=[...]` inserted right after its points. Edit Sketch opens on the Edit Points tool, but the drawing tools work there too, so a hole can be added to an existing sketch. Delete rules: deleting from a triangle removes the loop, Shift+double-click removes a whole loop (the only sane way to drop a 32-point circle), and the last loop of a committed sketch can't be deleted. Double-click delete only works with Edit Points. With a drawing tool, a click on a handle counts as a click on that point, so a rectangle can start on another loop's corner.

**Snapping.** The session's closed loops are snap targets like existing geometry (vertices, midpoints, edges). The loop being dragged is left out. The open polyline's own points stay alignment-only, as before. A tool's pending clicks (a rectangle's first corner, a circle's center) also act as alignment references.

The button is hidden on an extruded sketch (offset() can't take 3D) and on one that already has an offset.

**Undo.** A tool's pending click isn't sketch geometry, so Undo drops it first, then steps back through geometry as before.

## M8 build notes (2026-11-24) — custom module auto-toolbar

**What shipped.** A "Custom" toolbar section (purple rule on its left) lists every top-level `module` in the open document and in the files it `use`s. Clicking one appends a named-argument call, e.g. `bracket(w = 20, h = 10, thickness = 3);`, renders it and selects it, through the same insertion path as the built-in tools. Parameters whose default is `undef` are left out of the inserted call (passing undef is the same as omitting it; BOSL2 has a dozen per module); the panel still lists them. A tooltip shows the module's signature, where it is defined and the comment above it. Past 12 modules (a big library) a filter box appears. The parameter panel now names positional arguments from the module's definition (`bracket(30, 15, 4)` reads w/h/thickness, no more `#1/#2/#3`) and from a small table of built-in signatures (`cube([1,2,3], true)` reads size/center). For a custom module it also lists the parameters the call leaves out, showing their defaults; editing one adds it as a named argument. Widgets follow PLAN.md's rule: checkbox for a boolean default, number field for a number (plus a 0-360 slider when the parameter is used inside `rotate()`/`rotate_extrude()` or `sin`/`cos`/`tan`, or is named like an angle), X/Y/Z fields for a 3-vector, a text field for a string (the panel handles quoting and escapes), and a plain expression field otherwise. A widget is used only while the current text fits it, so an expression like `w * 2` in a number parameter falls back to the plain field instead of being lost. A required parameter (no default) gets its widget from the shapes existing calls pass for it, and an inserted call uses one of those values, else `undef` for the user to fill in.

**Code.** One `ToolDefinition` shape (`tools.ts`) now describes built-in and custom tools alike, with `insertTool` as the single insertion path (M5's append, plus a `use` directive when needed). `moduleIntrospection.ts` reads module definitions, call sites and widgets from tree-sitter trees; `paramPanel.ts` builds the panel's fields; `targetedPatch.ts` gained `addNamedArgument`. In the main process, `moduleSources.ts` finds the library files and a `chokidar` (v5) watcher, re-pointed after each scan, sends `modules:changed` when one is edited, created or deleted, which rescans the toolbar and re-renders (a used file's geometry may have changed too). Package split note: as with the rest of the build, these are files in `apps/desktop`, not the planned `module-introspection/` package.

**OpenSCAD scoping, checked against the bundled engine rather than assumed.** `use <a.scad>` makes a's modules callable and also those of every file a `include`s (an include is pasted text). `use` is *not* transitive: if a.scad itself does `use <b.scad>`, calling a b module from the document gives "Ignoring unknown module". Such modules are still offered (in italics); inserting one also adds the `use` the document needs, after its existing directives, written relative to a library folder if the file is in one, else relative to the document. So the isolated render gets the directive through the existing context prepend, and the saved file works in desktop OpenSCAD too. `test/integration/moduleSources.test.ts` pins both rules by rendering through `scad:render`. Leading-underscore modules (the usual library-private convention, used by BOSL2 and MCAD) are hidden. A module defined both in the document and a library resolves to the document's, matching OpenSCAD.

**Built-in positional names were checked, not copied from the manual.** Each entry of `BUILTIN_SIGNATURES` is pinned by `builtinSignatures.test.ts`, which renders the positional call and the named one and compares bounding boxes. This caught one real difference: in this engine `linear_extrude`'s second positional argument is not `center`, so only `height` is named positionally.

**Grammar gaps in real libraries.** Run against the corpus (`test/corpus/customModules.test.ts`), the plain tree found only 106 of BOSL2's modules: tree-sitter's error recovery swallows hundreds of lines into one ERROR node around constructs the grammar lacks (e.g. `assert(...) let(...)` chains), hiding every module inside. So when a file has errors, each line-leading `module name(` the tree missed is re-parsed on its own (up to the next top-level `module`/`function`), and if its own body has a gap, its signature alone (`module name(params) {}`). Result: 292 of 292 textual modules in the files `std.scad` includes, plus 204 tools across MCAD. Library analysis (definitions plus call sites) is cached per file and contents, because redoing it for BOSL2 on every render took about 0.6 s; the first scan of BOSL2 takes about 2 s.

**Finding for M13: BOSL2 only works through `include`.** `use <BOSL2/std.scad>` lists BOSL2's modules, but every call fails in the engine ("Ignoring unknown variable \"$anchor_override\""): BOSL2 relies on top-level variables and constants, which `use` does not import, and its own docs say to `include` it. With the "only `use`d modules" decision, a file that does `include <BOSL2/std.scad>` gets no BOSL2 tools. M13 (BOSL2 fillets/chamfers) will need either an exception for known include-style libraries or its own BOSL2 tool set.

**Not in M8.** Nested-module internals (drill-in is M9). Insertion still appends at the end of the document (as M5). A library file with grammar errors still yields the modules the parser can read, including ones inside a top-level error node.

## M9 build notes (2026-11-25) — drill-in navigation

**What shipped.** Select a boolean, a group block, an extrusion, a transform with a block, or a call of a module defined in the document or a `use`d file, then click "Open Difference #2 ▸" (or double-click it in the viewport). Its children become the working set: they are the only selectable, gizmo-able nodes, the rest of the model is drawn dim grey and see-through, and the editor dims the text outside the focused statement. A breadcrumb at the bottom left ("Assembly › bracket() #1 › Difference #1") links back to every level, the last crumb is the current location, and Escape steps out one level (and reselects the node you came from). Inside a difference the base is drawn see-through, and a click on it passes through to a cutter behind it, so cutters can be picked.

**Code.** `drillIn.ts` holds the model. A `WorkingSet` is the nodes of one level plus what an isolated render of one of them needs: the frame (the ancestors' literal translate/rotate/scale/mirror/multmatrix as one matrix), the context of each level (assignments and nested module definitions in a block body), and for a module body a scope. `drillInto` builds the next level, `resolveFocus` re-derives every level after each parse, and `isolatedRender` builds the engine source for one node. App.tsx renders the working set first, then the dimmed context, through a per-node render cache keyed by the exact source sent to the engine (LRU, 500 entries; cleared when a `use`d file changes on disk or the open file changes). Editing one child therefore costs one engine call: its siblings and the context hit the cache (checked by the e2e through `window.__scadstudioRenderStats`).

**Module bodies render in their real scope.** A node inside `module bracket(w=20, h=10)` is rendered as `module __scadstudio_scope_1(w=20, h=10) { <body assignments>; <node> } __scadstudio_scope_1(<the call's own args>) <the call's children>`, so parameters, defaults, `children()` and body variables all evaluate as in the full model. `drillInRender.test.ts` checks each case (boolean child, module args, block assignments, 2D extrude child, `children()`, a mirrored two-level case, a baked frame) against the engine's own full render by bounding box.

**Computed transforms are baked, not guessed.** When an ancestor's transform isn't a literal (`translate([w/2, 0, 0])`, a `for` variable), the frame stops there and the rest of the ancestor chain is prepended to the render source as text instead. The geometry is right, but the gizmo and the Position/Rotate/Mirror controls are off in that set (a banner says why); the parameter panel still edits.

**Library modules are view-only** (Jordan's decision). Drilling into a module from a `use`d file shows its internals with the editor read-only, the toolbar's editing groups hidden and the parameter panel disabled, and a banner with an explicit "Open parts.scad to edit" button that opens the library file (with the unsaved-changes check). Drilling into a module defined in the document edits its definition, with a banner that the change applies to every call.

**Node identity (risk 5).** `nodeIdentity.ts` carries a selection or a focus level across an edit: an LCS over the set's statement texts pins what didn't change, and a changed node is paired inside its gap by text similarity (character-pair Dice), the same call name, and the same offset. A focus level whose node is gone is left, with "Left drill-in (that node no longer exists)" in the status. A half-typed parse never moves the focus: only a clean parse commits a remap. After a typed edit the still-selected meshes glow for 600 ms (the confirm-flash), so a wrong guess shows.

**Structural edits at any depth (risk 4).** `wrapInBoolean`, `wrapInExtrude`, `patchTransform` and the new `insertIntoContainer` now follow the file's own indentation (4 spaces, 2 spaces or tabs) at any nesting depth. `insertIntoContainer` adds a toolbar insert or a finished sketch inside the focused node: after the last child at the children's indentation, opening a one-line `{ ... }`, or turning a single-statement body (`union() cube(1);`) into a block. `structuralEdits.property.test.ts` (fast-check, 120 runs by default, `PROPERTY_RUNS` to raise it) generates documents with nested booleans, blocks, transforms, modifiers, comments and a module, and checks every edit on every reachable working set: a clean parse, the intended read-back, nothing outside the edited statement changed. It found one real bug, fixed: inserting into a module body took its indentation from the call site instead of the definition. (Wrap-in-boolean's old top-level-only indentation was rewritten for nesting before the property tests existed.)

**Render latency (risk 2).** Drill-in adds no engine calls when nothing changed (every level is a cache hit), and an edit inside a set re-renders only the edited node. Entering a module for the first time costs one call per body statement plus the context; the 12-part boolean budget test still passes.

**Sketch mode reuses the focus.** Starting a sketch while drilled in shows "› Sketch" as one more crumb, and Finish Sketch writes the polygon into the focused node, converted into its frame (`worldToFrame`); Edit Sketch on a nested sketch converts back (`frameToWorld`). Escape leaves an untouched sketch; with changes it only says to Finish/Save or Exit/Cancel first, so nothing is lost.

**The M6 stopgap.** There was nothing to remove: M6's per-child selection was rescoped into M9 before a stopgap was built.

**Known limitations.** `for` bodies and `children()` targets can't be drilled into (`if` bodies can since the module-heavy follow-up below). A library module's own top-level variables aren't visible inside the scope wrapper, so a library body that reads them renders wrong while drilled in (the full model is unaffected). A baked outer transform that names a variable shadowed by a module parameter of the same name would resolve to the parameter. `rotate_extrude` profiles are drawn in XY, not swept. Typing inside the editor moves the cursor, which drives selection as before.

## M9 follow-up (2026-11-25) — module-heavy files

Jordan's rack mount (`apps/desktop/test/fixtures/rack_mount_single_keystone.scad`) builds the whole part inside one module, `switch_mount()`, out of eight modules defined *inside* it, and calls it once at the end through `if ($preview) { rotate/translate switch_mount(...) } else { switch_mount(...) }`. On M9 the whole part was one selectable blob: the only top-level statement was that `if`, which couldn't be drilled into, and even drilled into `switch_mount()` by hand, `main_body()`/`switch_cutout()`/... couldn't be opened because only top-level modules were looked up. What changed:

- **`if` statements drill in.** The working set is the statements of both branches. Each renders under its branch's condition (and the branch block's own assignments), so the branch the model doesn't take renders empty, the same way OpenSCAD would. OpenSCAD only accepts module definitions at the top level, in a bare block or in a module body, never inside an `if` block, and the render source nests scope wrappers (module definitions), so a guarded body goes into its own `module __scadstudio_branch_N()` defined where the `if` sits, and only its call is guarded (`children()` passed through inside a module scope). `else if` is the else branch's one statement, drillable in turn.
- **`$preview` is known statically**: ScadStudio always renders the exported part, so `$preview` is false. A statement in a `$preview` branch that isn't taken is not sent to the engine at all, inserts go into the branch the part takes, and a note says which branch is the part ("the else branch is the part as rendered and exported... the if branch only poses it for OpenSCAD's F5 preview"), also on every level inside it.
- **Nested modules resolve by name**, the way OpenSCAD looks them up: enclosing blocks first (`main_body` inside `switch_mount`), then the top level and used files (`resolveCall`). A selected call of a document module (nested or not) gets **Go to <name>() definition**, which selects the definition's name in the editor without dropping the viewport selection.
- **Show parts** (the "part to render" idea, scoped down): for the selected node, or the last top-level statement with nothing selected, drill through every level that holds exactly one statement in use (statically inactive branches and `*` don't count) and stop at the first level with several. On the rack mount that is Assembly › If ($preview) › switch_mount() › Translate, showing the body (the difference) and the keystone. A file with several top-level parts already has them as separate nodes, so no picker was built; this can grow into one if files with several candidate parts turn up.
- **Empty is not a failure.** A node whose render is empty (a false `if (front_wire_holes)`, an unused branch) counts as "Rendered (1 empty)" instead of "Rendered 5/6 nodes — ... Current top level object is empty".
- **Camera fit on open waits for the render.** Fitting fired when the path changed, before the new file had rendered, so it framed the previous document and the 254 mm part opened with the camera inside it.

Tests: `test/unit/moduleHeavy.test.ts` (if drilling, guards, static `$preview`, nested lookup, Show parts path, insert branch), `test/integration/moduleHeavyRender.test.ts` (the fixture's parts against OpenSCAD's own full render by bounding box; the false flag renders empty) plus four `if` cases in `drillInRender.test.ts`, and `test/e2e/m9-module-heavy.spec.ts` (open, fit, Show parts, the note, highlight pixels on a selected sub-module call, Go to definition, cutters). ## M15 build notes (2026-11-25) — text() and fonts

Decided with Jordan in the M15 thread: bundle Liberation Sans/Serif/Mono (OpenSCAD's own default fonts, OFL); model fonts are written in the code (`text(font="...")`) and picked from the Text panel, which lists bundled, project (`use <font.ttf>`) and installed fonts; Settings > Fonts sets the *code editor's* font and size, not model fonts; flat 2D Text (the CAD convention: sketch text, then extrude), no one-click 3D Text.

- **Engine swap.** A spike showed `openscad-wasm@0.0.4` already had fontconfig/FreeType/HarfBuzz compiled in and only lacked font files, but it **aborts the whole WASM module** (`RuntimeError: null function or function signature mismatch`) on any TrueType font without a hinting program (no `fpgm`/`prep`), which is most modern fonts (checked with Source Code Pro). Cause: OpenSCAD loads glyphs with `FT_LOAD_DEFAULT`, which sends unhinted fonts through FreeType's autohinter, whose function-pointer casts trap under WebAssembly. `@lofcz/openscad-wasm` (pinned to exactly 0.0.2; npm provenance: built by GitHub Actions from lofcz/openscad-wasm commit 911478e; OpenSCAD 2026.09.03, Manifold 3.5.1) carries the one-line fix (`FT_LOAD_NO_HINTING`) as a patch. All of the app's engine use now goes through `src/main/engine.ts`, so switching engines touches that file only. The new engine defaults to Manifold; the app still passes `--backend=Manifold`. Upstream: openscad/openscad#7289 (issue) plus a one-line PR from Jordan's fork (branch `freetype-no-hinting`); a weekly project thread watches for it to land in an official openscad-wasm build, at which point the app should switch back.
- **The engine compiles once per render process.** `engine.ts` compiles the `.wasm` once and instantiates it per render (still a fresh instance per render, the M0 rule): creating an instance dropped from ~75 ms to ~10 ms.
- **Fonts in each render** (`scadRender.ts` `mountFonts`, `fontStore.ts`): the bundled fonts always go into `/fonts` (the package's `addFonts()` hex-decodes ~4 MB per call, ~500 ms, so it runs once against a recording stand-in filesystem and the bytes are replayed, ~1 ms). Installed fonts are not all copied (system font folders can be hundreds of MB and fontconfig re-reads every file on each engine start): the main process indexes font *names* once (`fonts.ts`, reading each file's `name`/`post` tables, .ttf/.otf/.ttc), and a render gets only the families whose names appear as a string literal in the document or its libraries, which also covers `f = "Arial"; text(font=f)`. A name built at run time (`str("Ari", "al")`) is not found. Font bytes are cached in the render process (path + size + mtime, 512 MB cap).
- **`use <font.ttf>`** is OpenSCAD's way to register a font file. `collectDependencies` and the M8 module scan read every `use` target as UTF-8 SCAD, which would have garbled a font; font paths are now skipped there and mounted as binary at their mirrored path by `collectFontDependencies`.
- **A font that isn't installed** still renders: fontconfig substitutes a font silently (no warning in OpenSCAD's log), so the Text panel shows "Not installed here: renders in a substitute font" instead.
- **text() positional parameters** are only `text, size, font` (OpenSCAD's `TextNode.cc`; the engine ignores a 4th positional). `ToolParam.namedOnly` keeps the panel from naming a 4th positional argument `halign`. The panel lists `font`, `halign`, `valign` and `spacing` with their defaults even when the call doesn't pass them (`LIST_UNSET_BUILTINS`). New widgets: `font` (grouped picker) and `choice` (alignment).
- **Sketch mode Text**: one click places `text()` on the sketch plane, the click folded into the plane's own `translate()` so the statement is the canonical `translate() rotate() text()` wrap. With nothing else drawn, sketch mode ends with the text selected; otherwise the loops drawn so far stay.
- **Settings** (`src/main/settings.ts`): the app's first persisted settings, `settings.json` in Electron's userData folder. The e2e fixture gives each launch its own folder (`SCADSTUDIO_USER_DATA`) and a known "installed" font folder (`SCADSTUDIO_SYSTEM_FONT_DIRS`, the test fixtures).

Tests: `test/unit/fonts.test.ts` (name tables, bundled list matches the package, folder scan, which fonts a document names, settings), `test/unit/fontOptions.test.ts` (picker groups and matching), additions to `paramPanel`/`primitives` unit tests, `test/integration/fonts.test.ts` (default/bundled/styled fonts render, the unhinted fixture renders, `use <font.ttf>`, installed fonts through `scad:render`, the memory cache), `builtinSignatures.test.ts` (text's positional order and named-only halign), `engine.test.ts` (new Manifold default; text() needs mounted fonts), and `test/e2e/m15-text-fonts.spec.ts`. The unhinted fixture is Adobe's Source Code Pro (OFL, `test/fixtures/fonts/`). Screenshots: project files `text-fonts/`.

## M11 build notes (2026-11-25) — directional constraints

Built to the eight decisions above. Everything writes plain OpenSCAD: variables at the top of the file and expressions in `translate()`/`for`, so the file still opens in OpenSCAD and its Customizer.

- **Expression evaluator** (`scadExpr.ts`). The app now evaluates expressions in transforms and arguments instead of treating any non-literal as baked. Checked case by case against the engine's own `echo()` output (`test/integration/scadExpr.test.ts`): trigonometry in degrees, `-a^b` is `-(a^b)`, `round` rounds halves away from zero, user functions, `let`, list comprehensions, ranges. Two grammar quirks are worked around by re-parsing the bracket text: `[0:2:6]` parses as a nested range and `[0 : n - 1]` as `(0:n) - 1`. `$t` and other special variables are unknown.
- **Expression axes.** `NodeTransform.exprs` keeps each translate/rotate/scale component's text. `patchTransform` keeps an expression unless the edit replaces it. The Position fields are text: typing an expression writes it, typing a number detaches the axis. The gizmo hides the handle of an expression axis (decision 8; `gizmoLocks.ts`); rotation locks as a whole, and translate splits per axis only in an axis-aligned frame. `color()` and `mirror()` still read literals only. A negative expression scale stops the transform walk.
- **Variables** (`variables.ts`, `VariablesPanel.tsx`): top-level assignments with their Customizer annotation, group, description (a `//` line above, not the previous line's trailing annotation) and uses. Uses skip definitions, argument names, call names and shadowed names. Rename rewrites every use. Delete of a used variable lists the lines and offers to inline the value in parentheses. Sliders commit on release, because the render cache is keyed on the whole source and every variable edit re-renders every part. The panel remembers whether it was open.
- **Visible scopes** (Jordan, 2026-11-25, added before release): the panel has a *This file* section, an *Inside name()* section for the module the editor cursor or drill-in is in (parameters read-only, since each call sets them; local variables editable, and rename/delete stay inside the module), and a read-only *From file.scad* section per included file (`scanIncludes` in `moduleSources.ts`, nested includes too, not uses). Checked on the engine: included variables (nested too) are visible to the document; a used file's are not (`cube(used_var)` renders the default 1 mm cube). Drilled into a library module, its variables show read-only. Variables were not made file-wide: a module's variables mean something only inside it.
- **Make variable** (ƒx next to parameter and Position fields): names the value `<call>_<param>`, writes it into the top block and replaces the literal.
- **Distance / Align** (`relate.ts`, `extents.ts`, `linExpr.ts`, `ToolPanel.tsx`): the docked panel has a Move slot (orange, the selection color) and a Relative to slot (red, the operand color); clicking a slot then a part re-picks it. Axis, which edge of each part (min/center/max), the distance and an optional variable name. Extents are symbolic for cube, sphere, cylinder, square and circle under 90°-multiple rotations and scales; anything else uses the measured box and the preview says it won't follow (decision 3). "Follow changes" names the reference's translate and the sizes the expression reads as variables (`cube_x`, `cube_width`, `sphere_r`), so editing them moves the part. Only names that survive into the final expression are created. Note: the reference's translate then becomes a bare variable, which locks that gizmo axis.
- **Pattern** (`pattern.ts`): linear `for (i = [0 : n - 1]) translate([i * pitch, 0, 0])` (pitch by default; Gap adds the part's width along the axis to the typed gap and writes that as the pitch) and circular `for (i = [0 : n - 1]) rotate([0, 0, i * 360 / n])`. Selecting a pattern shows its count and spacing in a strip to edit. A top-level `for` is its own primitive in `decomposeNode`, so the gizmo and Position move the whole pattern by prefixing a `translate()`; it is not drillable.
- **Linked drag** (Jordan, 2026-11-26, from testing): Distance with Follow locks the parts together on every axis: the moved part's other two translate components become the reference's position variables plus today's offset (`translate([cube_x + cube_width + gap + sphere_r, cube_y + 5, cube_z])`). An expression axis drags when it is `anchor + ...`, where the anchor is a position variable (a top-level variable assigned once to a number that some part uses as its whole translate component on that axis); dragging moves the anchor's number by the drag distance, so every linked part moves and the distance stays (`linkedDrag.ts`). Align keeps its single axis. Other expression axes stay locked. Known: the linked part jumps into place on release rather than moving live during the drag.
- **Distance and Align are experimental** (Jordan, 2026-11-26): shipped in beta-v0.1.6 with an "experimental" tag in the toolbar and tool panel. Revisit them with the constraint solver (M12): face picking and dimension lines are M10d (see the M10 breakdown), and the solver should decide whether these tools become solver constraints. What they write is plain OpenSCAD, so files made with them keep working either way.
- **Layout cost**: at 1280 px the toolbar now wraps to three rows when a part is selected (Constrain row plus the Position ƒx buttons). M10 should fold it.

## CI/CD: AppImage builds (2026-09-07)

Added `.github/workflows/build-appimage.yml`: on every push to `master` (plus manual `workflow_dispatch`), it typechecks, builds, packages a Linux AppImage via `electron-builder`, **actually launches the packaged AppImage headlessly under Xvfb as a smoke test** (not just trusting a successful build), and uploads both the AppImage and the smoke-test screenshot as downloadable workflow artifacts.

**Why the smoke-test step matters, not just "nice to have"**: `electron-builder`'s main-process dependency bundling depends on correctly resolving this repo's npm-workspace-hoisted `node_modules` (the app's own `package.json` lives in `apps/desktop/`, but the actual installed packages sit at the repo root). A build can complete successfully and produce a plausible-looking AppImage while still being missing a runtime dependency the main process needs (e.g. `openscad-wasm`, which `main/index.ts` imports as an external, unbundled specifier via electron-vite's `externalizeDepsPlugin()`) — that failure mode only shows up when the packaged app is actually launched, not at build time. Verified locally first (extracted the AppImage via `--appimage-extract`, ran `./squashfs-root/AppRun` under Xvfb with the same swiftshader flags used for milestone verification, confirmed the default example renders identically to the dev build) before trusting the same steps in CI.

**Config specifics that mattered**:
- `electron` must be a **pinned exact version** in `package.json` (`"44.1.1"`, not `"^44.1.1"`) — electron-builder needs to resolve a specific release to download platform binaries for, and refuses to proceed from a semver range.
- `executableName` must be set explicitly in `electron-builder.yml` — it defaults to a sanitized `package.json` "name", and this package is scoped (`@scadstudio/desktop`), which produces an invalid filename (`@scadstudiodesktop`).
- electron-builder's own dependency scan correctly walks up to the npm workspace root to resolve `node_modules` — confirmed via its build log (`detected workspace root for project using lock file`) and by verifying `openscad-wasm` actually ends up packed inside `app.asar`. No special monorepo configuration was needed beyond letting it do its default scan (the `files` list only needs to name the build output, not `node_modules`).
- Ubuntu's ALSA package was renamed (`libasound2` → `libasound2t64`) across recent versions — installed as an isolated fallback (`libasound2t64 || libasound2`) in the smoke-test step's apt install, since a single failed package name aborts an entire `apt-get install` batch (the same gotcha hit earlier in this container's own environment setup).

**Update 2026-09-09: added a Windows build alongside Linux**, on request (Jordan works from both platforms). Renamed the workflow file/name to `build-desktop.yml` / "Build Desktop Apps" since it's no longer Linux-only. Restructured into three jobs: `build-linux` (unchanged), a new `build-windows` (on `windows-latest`), and `release` (needs both, only runs on a tag push) — split out `release` specifically so the two platform jobs, which run in parallel, don't race to create the same GitHub Release.

- **Windows target is `portable`** (electron-builder), not an NSIS installer — a single self-contained `.exe` that self-extracts to `%TEMP%` and launches, matching the AppImage's "just run it, no install" spirit. Unsigned (no code-signing cert), so Windows SmartScreen shows an unrecognized-publisher warning on first run — acceptable for a private beta, revisit if this ever ships more broadly.
- **`electron-builder --win portable` needed no Wine at all**, cross-building cleanly from this Linux dev container — worth knowing since NSIS installer targets commonly *do* need Wine on Linux; `portable` apparently doesn't invoke `makensis` the same way. Verified locally first, same practice as every other packaging step in this file: real build (118.8MB, correct order of magnitude for a full Electron+Chromium app), confirmed valid via `MZ`/`PE` header bytes, not just "the command exited 0."
- **Real mistake caught before it became a false alarm**: an accidental *second* concurrent `package:win` run against the same `dist/` output directory produced a corrupted 338KB `.exe` (valid `MZ` header, but the NSIS embedding step never actually ran) — looked exactly like a real packaging bug until a clean, single re-run produced a correctly-sized file. Lesson: don't run packaging commands concurrently against a shared output directory; if a build result looks implausibly small, check for a stray concurrent process before assuming the config is wrong.
- **Windows smoke test uses `shell: bash`** (Git for Windows ships one on `windows-latest` runners) rather than PowerShell, specifically to reuse the same `SCADSTUDIO_SCREENSHOT` env var + `timeout` + exit-code-checking approach already proven on Linux, rather than writing and debugging a second, PowerShell-flavored verification path from scratch. Software-rendering flags (`--disable-gpu --use-gl=swiftshader`) mirror the Linux job's, since `windows-latest` runners are also GPU-less.
- **Took four pushes to actually prove real geometry renders on Windows, not just "the process exited 0"** — each one caught by inspecting the actual output artifact rather than trusting a green checkmark: (1) first run technically passed but the screenshot artifact silently never uploaded (the `/tmp` vs `$RUNNER_TEMP` path bug above); (2) once visible, that screenshot showed the UI chrome correctly but an *empty viewport still reading "Rendering..."* — this runner's WASM compile/render is measurably slower than Linux's, so the fixed 3-second wait in `main/index.ts`'s screenshot hook (reliable since M1) wasn't enough; (3) replaced it with a poll loop for the real "Rendered" status text, but the outer `timeout 30` wrapping the whole process wasn't widened to match, so it killed the app mid-poll before it ever reached the screenshot capture; (4) widened the outer timeout to 90s and the poll ceiling to 60s — confirmed on run [34295970969](https://github.com/TheSingularis/scadstudio/actions/runs/34295970969), screenshot shows all three shapes fully rendered, status reading "Rendered", matching the Linux job's output. The pattern across all of this: a "passing" CI job proves nothing about *content* unless something actually looks at what it produced.
- **Real bug caught on that same first run**: the smoke-test screenshot path was hardcoded to `/tmp/smoke-win.png`. Bash (via Git-Bash's own path translation on Windows) resolved that fine, so the smoke test's own assertions all passed — but the separate `actions/upload-artifact` step runs as a native Node action, not through Git-Bash, and couldn't resolve the same Unix-style path (`No files were found with the provided path`, silently skipped since `if-no-files-found: ignore`). The build/launch/render verification was never actually compromised, but the screenshot artifact — the thing that lets a human actually *look* at what rendered — quietly never uploaded. Fixed by using `$RUNNER_TEMP` (a GitHub Actions env var pointing at an OS-native temp path, understood identically by bash steps and native actions on every platform) instead of a hardcoded `/tmp` path.
- **A second real bug, caught by actually looking at the now-uploading Windows screenshot rather than trusting the smoke test's pass/fail**: the screenshot showed the UI chrome rendered correctly but an *empty* 3D viewport, status still reading "Rendering..." — the same fixed 3-second `setTimeout` in `main/index.ts`'s screenshot hook (there since M1, used for every prior milestone's Linux verification) that reliably finishes on Linux CI isn't enough time on `windows-latest`'s evidently-slower WASM compile/render path. This wasn't a smoke-test false pass exactly (no error text, valid-sized PNG — the literal assertions held) but it meant the screenshot never actually proved real geometry rendered on Windows, undermining the entire point of a *visual* smoke test. Fixed by replacing the fixed delay with a poll loop (`document.body.innerText.includes("Rendered")`, up to a 20s ceiling) so the screenshot hook waits for the app's own real completion signal instead of guessing a platform-specific number — benefits every future verification run on any platform, not just this one.
